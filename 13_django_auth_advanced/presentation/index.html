Аутентификация vs Авторизация

В сфере безопасности веб-приложений эти два понятия часто путают, но они решают совершенно разные задачи:

Аутентификация (Authentication)

Отвечает на вопрос: "Кто ты?".
Процесс проверки подлинности пользователя. Обычно происходит при вводе логина и пароля, проверке SMS-кода или токена.

Аналогия: Показ паспорта на паспортном контроле в аэропорту.

Авторизация (Authorization)

Отвечает на вопрос: "Что тебе разрешено?".
Процесс проверки прав доступа пользователя к конкретному ресурсу (странице, операции в БД, файлу).

Аналогия: Посадочный талон, определяющий ваше место в самолете и доступ в бизнес-лаунж.

Архитектура django.contrib.auth

Django поставляется со встроенной надежной системой пользователей. Она включена по умолчанию в settings.py:

# settings.py
INSTALLED_APPS = [
    ...
    'django.contrib.auth',
    'django.contrib.contenttypes',
    'django.contrib.sessions',
    ...
]

Система авторизации Django тесно связана с сессиями (sessions), которые позволяют серверу "помнить" вошедшего пользователя между запросами.

Основные поля встроенной модели User:

  • username — уникальное имя пользователя
  • email — адрес электронной почты
  • password — хэшированный пароль
  • is_staff — разрешен ли доступ в админ-панель
  • is_active — активен ли аккаунт (вместо удаления)
  • is_superuser — имеет ли все права без исключения

Программная аутентификация в Django

Если мы пишем вход вручную (например, в собственной View), мы используем три ключевые функции:

from django.contrib.auth import authenticate, login, logout

# 1. Проверяем логин и пароль. Возвращает объект User или None
user = authenticate(request, username='alex', password='secure_password_123')

if user is not None:
    # 2. Создаем сессию для пользователя (пользователь входит на сайт)
    login(request, user)
else:
    # Ошибка: неверные учетные данные
    pass

# 3. Выход из системы (уничтожение текущей сессии)
logout(request)

Встроенные контроллеры (Views)

Вместо написания своего кода для входа, выхода и смены паролей, Django предлагает готовые Class-Based Views в модуле django.contrib.auth.views:

Класс View Назначение Шаблон по умолчанию
LoginView Вход пользователя (форма + логика) registration/login.html
LogoutView Выход пользователя registration/logged_out.html
PasswordChangeView Смена пароля авторизованным пользователем registration/password_change_form.html
PasswordChangeDoneView Страница успешного изменения пароля registration/password_change_done.html

Настройка входа: LoginView

Шаг 1: Подключаем View в urls.py:

from django.contrib.auth import views as auth_views
from django.urls import path

urlpatterns = [
    path('login/', auth_views.LoginView.as_view(), 
         name='login'),
]
По умолчанию Django ищет шаблон по пути templates/registration/login.html.

Шаг 2: Создаем шаблон login.html:

<!-- templates/registration/login.html -->
<h2>Вход на сайт</h2>
<form method="post">
    {% csrf_token %}
    {{ form.as_p }}
    <button type="submit">Войти</button>
</form>

Django автоматически генерирует форму входа с полями username и password и передает ее в контекст как form.

Выход из системы: LogoutView

Подключение в urls.py аналогично:

urlpatterns = [
    path('logout/', auth_views.LogoutView.as_view(), 
         name='logout'),
]
Важное изменение в Django 5.0+:
Вход по GET-запросу на URL выхода больше не работает. Выход должен осуществляться строго через POST-запрос с целью защиты от несанкционированного разлогинивания сторонними сайтами.

Правильный способ реализации кнопки выхода в шаблоне:

<form action="{% url 'logout' %}" method="post">
    {% csrf_token %}
    <button type="submit">Выйти из аккаунта</button>
</form>

Если нужно перенаправить пользователя после выхода, укажите в settings.py:
LOGOUT_REDIRECT_URL = 'home'

Регистрация пользователей

В Django нет встроенной View для регистрации, но есть готовая форма UserCreationForm. Нам нужно написать контроллер самостоятельно:

# views.py
from django.contrib.auth.forms import UserCreationForm
from django.urls import reverse_lazy
from django.views.generic import CreateView

class SignUpView(CreateView):
    form_class = UserCreationForm
    success_url = reverse_lazy('login')
    template_name = 'registration/signup.html'
# urls.py
from .views import SignUpView

urlpatterns = [
    path('signup/', SignUpView.as_view(), 
         name='signup'),
]
UserCreationForm автоматически проверяет сложность пароля, совпадение паролей и уникальность имени пользователя.

Ограничение доступа: @login_required

Как сделать страницу доступной только для авторизованных пользователей? Для Function-Based Views (FBV) используем декоратор:

from django.contrib.auth.decorators import login_required
from django.shortcuts import render

@login_required
def profile_view(request):
    # Если пользователь не вошел, он автоматически перенаправляется на страницу входа
    return render(request, 'profile.html', {'user': request.user})

В settings.py нужно настроить путь к странице авторизации:
LOGIN_URL = 'login'

Django автоматически добавляет GET-параметр ?next=/profile/ в URL входа, чтобы перенаправить пользователя обратно после авторизации.

Ограничение доступа: LoginRequiredMixin

Для Class-Based Views (CBV) декораторы использовать неудобно. Вместо этого применяется класс-примесь LoginRequiredMixin:

from django.contrib.auth.mixins import LoginRequiredMixin
from django.views.generic import TemplateView

class ProfileView(LoginRequiredMixin, TemplateView):
    template_name = 'profile.html'
    
    # Можно переопределить адрес страницы входа прямо в классе:
    # login_url = '/login/'
    # redirect_field_name = 'redirect_to'
Правило наследования: LoginRequiredMixin всегда должен наследоваться первым (слева направо) перед другими базовыми классами View (например, TemplateView, ListView и т.д.).

Права доступа (Permissions)

Права доступа (Permissions) определяют возможность выполнения действий. Для каждой модели Django автоматически создает 4 права:

  • add (добавление): например, blog.add_post
  • change (редактирование): например, blog.change_post
  • delete (удаление): например, blog.delete_post
  • view (просмотр): например, blog.view_post
Системное имя права состоит из: <имя_приложения>.<действие>_<имя_модели>. Например: если в приложении store есть модель Product, то право на изменение будет store.change_product.

Проверка прав доступа в коде

Для FBV: декоратор @permission_required

from django.contrib.auth.decorators import \
    permission_required

@permission_required('blog.add_post', 
                     raise_exception=True)
def create_post(request):
    # Только пользователи с правом add_post
    return render(request, 'create.html')

Для CBV: миксин PermissionRequiredMixin

from django.contrib.auth.mixins import \
    PermissionRequiredMixin

class PostCreateView(PermissionRequiredMixin, 
                     CreateView):
    permission_required = 'blog.add_post'
    # При отсутствии прав вызовет 403 Forbidden:
    raise_exception = True
    ...

Права доступа в шаблонах

Django автоматически передает переменную perms в контекст всех шаблонов. Мы можем проверять права прямо при рендере HTML:

<!-- templates/post_detail.html -->
<h1>{{ post.title }}</h1>
<p>{{ post.content }}</p>

{% if perms.blog.change_post %}
    <a href="{% url 'post_edit' post.id %}">Редактировать статью</a>
{% endif %}

{% if perms.blog.delete_post %}
    <a href="{% url 'post_delete' post.id %}" style="color:red;">Удалить</a>
{% endif %}

Группы пользователей (Groups)

Назначать права каждому пользователю отдельно неудобно и долго. Для этого существуют Группы.

Группа — это набор разрешений (прав). Любой пользователь, добавленный в группу, автоматически наследует все ее права.

Обычно группы создаются в панели администратора Django (например, "Редакторы", "Модераторы", "Менеджеры"), там же им назначаются соответствующие права на модели.

Работа с группами в коде Python:

from django.contrib.auth.models import Group

# Найти или создать группу
editors, created = Group.objects.get_or_create(
    name='Editors'
)

# Добавить пользователя в группу
user.groups.add(editors)

# Проверить, состоит ли пользователь в группе
is_editor = user.groups.filter(name='Editors').exists()

Смена и сброс пароля

Django предоставляет полноценный рабочий цикл смены и сброса паролей из коробки. Достаточно подключить URLs:

# urls.py
urlpatterns = [
    # Смена пароля (для авторизованных)
    path('password-change/', 
         auth_views.PasswordChangeView.as_view(), 
         name='password_change'),
    path('password-change/done/', 
         auth_views.PasswordChangeDoneView.as_view(), 
         name='password_change_done'),
]

Для сброса забытого пароля используются: PasswordResetView, PasswordResetDoneView, PasswordResetConfirmView, PasswordResetCompleteView.

Сброс пароля по Email:
Django генерирует временную одноразовую защищенную ссылку и отправляет ее пользователю на почту. Для тестирования этого процесса можно отправлять письма прямо в консоль, прописав в settings.py:
EMAIL_BACKEND = 'django.core.mail.backends.console.EmailBackend'

Хранение паролей и Безопасность

Почему нельзя хранить пароли в чистом виде?

В случае утечки базы данных злоумышленники получат доступ ко всем аккаунтам. Более того, многие используют одинаковые пароли на разных сайтах.

Django никогда не хранит пароли в открытом виде. Он сохраняет только криптографический хэш пароля.

Как выглядит сохраненный пароль в БД Django:

pbkdf2_sha256$870000$pG7yXq...$A9xB3c...

Компоненты хэша:

  1. Алгоритм: PBKDF2 c SHA256.
  2. Итерации: 870 000 повторений хэширования (защита от брутфорса).
  3. Соль (Salt): случайная строка для защиты от радужных таблиц.
  4. Сам хэш: результат вычисления.

Конфигурация редиректов в settings.py

Чтобы встроенные Views знали, куда перенаправлять пользователя после успешного действия, используются следующие переменные настроек:

# settings.py

# URL, на который перенаправляются неавторизованные пользователи (для @login_required)
LOGIN_URL = 'login'

# URL, куда перенаправляется пользователь ПОСЛЕ успешного входа на сайт
LOGIN_REDIRECT_URL = 'profile'

# URL, куда перенаправляется пользователь ПОСЛЕ выхода из системы
LOGOUT_REDIRECT_URL = 'login'

В качестве значений можно указывать как относительные пути ('/accounts/login/'), так и имена именованных URL-маршрутов ('login', 'profile'). Второй способ предпочтительнее!

Валидация паролей в Django

По умолчанию Django проверяет создаваемые пароли на надежность. Список правил задается в AUTH_PASSWORD_VALIDATORS:

# settings.py
AUTH_PASSWORD_VALIDATORS = [
    # 1. Проверка на сходство с личными данными (username, email, etc.)
    {'NAME': 'django.contrib.auth.password_validation.UserAttributeSimilarityValidator'},
    # 2. Проверка на минимальную длину (по умолчанию 8 символов)
    {'NAME': 'django.contrib.auth.password_validation.MinimumLengthValidator'},
    # 3. Проверка на распространенные пароли (в базе 20 000 популярных паролей)
    {'NAME': 'django.contrib.auth.password_validation.CommonPasswordValidator'},
    # 4. Проверка на чисто числовой пароль
    {'NAME': 'django.contrib.auth.password_validation.NumericPasswordValidator'},
]
При локальной разработке валидаторы можно закомментировать, чтобы вводить простые пароли вроде "123". Но на сервере они обязаны быть включены!

Чек-лист: Подключение авторизации

  1. Убедиться, что django.contrib.auth подключен в INSTALLED_APPS.
  2. Подключить LoginView и LogoutView в файле urls.py проекта.
  3. Создать директорию templates/registration/.
  4. Создать шаблон login.html с формой POST и токеном CSRF.
  5. Добавить настройки редиректов в settings.py.
Готово!

После выполнения этих шагов ваш сайт будет иметь полноценную защищенную авторизацию сессий, форму входа с проверками и безопасный выход.
