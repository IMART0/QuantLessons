Повторение кода: Нарушение принципа DRY

Представим модель мероприятия Event для нашего сайта лагеря:

# models.py
class Event(models.Model):
    title = models.CharField(max_length=100)
    description = models.TextField()
    is_public = models.BooleanField(default=True)

Если мы пишем обычную форму для ввода:

# forms.py
class EventForm(forms.Form):
    title = forms.CharField(max_length=100)
    description = forms.CharField(widget=forms.Textarea)
    is_public = forms.BooleanField(required=False)
Минусы обычных forms.Form:
  • Дублирование полей: Мы пишем одни и те же типы данных и ограничения (например, max_length) дважды.
  • Ручной перенос в БД: Во View приходится вручную доставать значения из cleaned_data и передавать их в модель.
  • Трудности поддержки: Добавили поле в модель? Придется руками дописывать его в форму и во View.

Решение: Django ModelForm

Django предоставляет класс ModelForm, связывающий форму с моделью напрямую.

ModelForm — это класс формы, который автоматически считывает метаданные указанной модели, строит на их основе HTML-поля с правилами валидации, а также предоставляет метод для сохранения данных в базу данных.

Основные плюсы:

  • DRY (Don't Repeat Yourself): Структура данных описывается только один раз — в модели.
  • Автоматическая валидация: Ограничения базы данных проверяются автоматически перед сохранением.
  • Интеграция с СУБД: Метод save() позволяет создать или обновить запись в один вызов.

Базовый синтаксис ModelForm

Чтобы сгенерировать форму на основе модели Event, наследуемся от forms.ModelForm и объявляем класс Meta:

from django import forms
from .models import Event

class EventForm(forms.ModelForm):
    class Meta:
        model = Event               # Указываем модель базы данных
        fields = ['title', 'description', 'is_public']  # Перечисляем поля
Класс Meta: Служебный класс внутри формы, определяющий её конфигурацию. Минимально обязательные параметры — это model и выбор отображаемых полей (fields или exclude).

Опции Meta: Выбор полей (fields)

Параметр fields указывает, какие именно поля модели будут выведены в HTML-форму:

  • fields = ['title', 'description'] — выводятся только перечисленные поля (явное указание).
  • fields = '__all__' — выводит все поля модели, присутствующие в БД.
Опасайтесь fields = '__all__'!
Если в вашей модели есть служебное поле (например, is_approved — "одобрено администрацией"), при использовании __all__ оно попадет на форму. Злоумышленник сможет подделать POST-запрос и одобрить свое мероприятие без модератора (уязвимость Mass Assignment). Всегда пишите список полей явно!

Опции Meta: Исключение полей (exclude)

Иногда проще указать, какие поля не нужно выводить в форму. Для этого служит опция exclude:

class EventForm(forms.ModelForm):
    class Meta:
        model = Event
        exclude = ['is_approved'] # Выведет все поля модели, кроме 'is_approved'

Важное правило:

  • В классе Meta должен присутствовать либо fields, либо exclude (хотя бы один из них).
  • Их нельзя использовать совместно в одном классе Meta. Рекомендуется использовать fields для большей безопасности.

Как поля модели превращаются в поля форм?

Django автоматически подбирает тип HTML-поля и правила валидации на основе типа поля в модели:

Поле в Model (БД) Поле в Form Стандартный HTML Widget
CharField(max_length=...) CharField <input type="text">
TextField() CharField <textarea></textarea>
BooleanField() BooleanField <input type="checkbox">
ForeignKey(to=...) ModelChoiceField <select> (выпадающий список)
ManyToManyField(to=...) ModelMultipleChoiceField <select multiple> (множественный выбор)

Кастомизация: Ярлыки (labels) и подсказки (help_texts)

Вы можете переопределить подписи полей и поясняющие подсказки непосредственно в классе формы:

class EventForm(forms.ModelForm):
    class Meta:
        model = Event
        fields = ['title', 'description']
        labels = {
            'title': 'Название лагерного мероприятия',
            'description': 'Подробное описание программы',
        }
        help_texts = {
            'title': 'Краткое название, понятное для детей (до 100 символов).',
        }

Кастомизация: Сообщения об ошибках

Можно переопределить стандартные тексты ошибок валидации через словарь error_messages:

class EventForm(forms.ModelForm):
    class Meta:
        model = Event
        fields = ['title']
        error_messages = {
            'title': {
                'required': 'Пожалуйста, введите название мероприятия, без него сохранить нельзя!',
                'max_length': 'Название не должно быть длиннее 100 символов.',
            }
        }
Это позволяет заменить технические системные ошибки Django на понятный русскоязычный текст для школьников и преподавателей лагеря.

Кастомизация виджетов: опция widgets

Для стилизации полей ввода (добавления CSS-классов вроде Bootstrap form-control или плейсхолдеров) используют словарь widgets:

from django import forms

class EventForm(forms.ModelForm):
    class Meta:
        model = Event
        fields = ['title', 'description']
        widgets = {
            'title': forms.TextInput(attrs={
                'class': 'form-control',
                'placeholder': 'Например: Турнир по робототехнике'
            }),
            'description': forms.Textarea(attrs={
                'class': 'form-control',
                'rows': 4,
                'placeholder': 'Опишите правила участия и расписание...'
            }),
        }

Альтернатива: переопределение полей класса

Если настроек виджетов в Meta недостаточно, можно объявить поле непосредственно в классе. Это перекроет поле из Meta:

class EventForm(forms.ModelForm):
    # Явно объявленное поле переопределяет настройки из Meta
    title = forms.CharField(
        max_length=50, # Сузили лимит в форме (в БД остался 100)
        label="Название события лагеря",
        widget=forms.TextInput(attrs={'class': 'custom-camp-input'})
    )

    class Meta:
        model = Event
        fields = ['title', 'description']
Внимание: При ручном переопределении не делайте форму лояльнее, чем база данных (например, required=False для обязательного в БД поля). Иначе СУБД вернет ошибку при сохранении.

Использование в View: Создание объекта

При создании объекта мы привязываем POST-данные к форме, проверяем валидность и сохраняем в БД:

from django.shortcuts import render, redirect
from .forms import EventForm

def event_create_view(request):
    if request.method == 'POST':
        form = EventForm(request.POST) # Привязываем данные из POST-запроса
        if form.is_valid():
            event = form.save()        # Сохраняем объект в базу данных!
            return redirect('event_list')
    else:
        form = EventForm()             # Пустая форма для GET-запроса
        
    return render(request, 'event_form.html', {'form': form})
Вызов form.save() автоматически выполняет SQL-запрос INSERT INTO, возвращая созданный экземпляр модели Event с присвоенным ID.

Использование в View: Обновление (Update)

Для редактирования существующей записи передаем объект в аргумент instance формы:

from django.shortcuts import get_object_or_404
from .models import Event

def event_update_view(request, pk):
    event = get_object_or_404(Event, pk=pk) # Загружаем объект из БД
    
    if request.method == 'POST':
        # Связываем форму с присланными данными и с исходным объектом:
        form = EventForm(request.POST, instance=event)
        if form.is_valid():
            form.save() # Делает UPDATE в БД для этой конкретной строки!
            return redirect('event_list')
    else:
        form = EventForm(instance=event) # Форма предзаполняется старыми данными
        
    return render(request, 'event_form.html', {'form': form})

Паттерн save(commit=False)

Иногда форма не содержит всех полей, обязательных для сохранения модели в БД. Например, поле организатора creator (ForeignKey на User) заполняется автоматически.

Прямой вызов form.save() вызовет ошибку IntegrityError из-за пустого поля creator_id.

Решение — отложенное сохранение:

  • Вызываем form.save(commit=False) — объект создается только в оперативной памяти Python.
  • Записываем недостающие данные программно: event.creator = request.user.
  • Вызываем event.save() для физической записи объекта в БД.

Как работает commit=False (Код)

Пример автоматического назначения текущего пользователя организатором лагерного мероприятия:

def event_create_view(request):
    if request.method == 'POST':
        form = EventForm(request.POST)
        if form.is_valid():
            # 1. Получаем объект, не записывая в СУБД:
            event = form.save(commit=False)
            # 2. Программно заполняем организатора:
            event.creator = request.user
            # 3. Теперь сохраняем физически:
            event.save()
            return redirect('event_list')
Этот шаблон проектирования используется повсеместно для автоматического заполнения полей авторов, дат создания, статусов или IP-адресов.

Сохранение Many-to-Many при commit=False

Если форма содержит ManyToMany-поля (например, теги мероприятия tags), при commit=False они не могут быть записаны в промежуточную таблицу (у объекта еще нет ID).

# Если у мероприятия есть теги (ManyToMany связь):
if form.is_valid():
    event = form.save(commit=False)
    event.creator = request.user
    event.save()           # Объект записан, ID получен
    form.save_m2m()       # Обязательно! Сохраняем связи Many-to-Many
Если вы используете commit=False при наличии в форме Many-to-Many связей, вы обязаны вызвать метод form.save_m2m() сразу после сохранения основного объекта! Иначе связи будут утеряны.

Отображение формы в HTML шаблоне

Для отображения формы на странице используем тег {% csrf_token %} и методы рендеринга полей:

<form method="post">
    {% csrf_token %}
    
    
    {{ form.as_div }}
    
    <button type="submit" class="btn btn-success">Сохранить мероприятие</button>
</form>
Метод form.as_div(): Оборачивает каждое поле в тег <div>. Это современный стандарт верстки, заменяющий устаревшие табличный (as_table) и абзацный (as_p) рендеры.

Итоги урока: Сравнение Form и ModelForm

Используйте forms.Form:

  • Форма не связана с БД напрямую (калькулятор смен, обратная связь без сохранения, фильтрация списков).

Используйте forms.ModelForm:

  • Форма служит для создания, редактирования или модерации записей базы данных лагеря (CRUD-операции).
Чек-лист разработки:
  1. Создать класс формы, унаследованный от forms.ModelForm.
  2. Прописать в Meta модель и список fields (явно!).
  3. При необходимости настроить виджеты, плейсхолдеры и ярлыки.
  4. Во View передать request.POST (и instance для редактирования).
  5. Вызвать form.is_valid() и сохранить объект методом form.save().
