Шаблоны в Django

Рендеринг динамического контента и разделение логики

Проблема: HTML внутри Python-кода

До сих пор мы возвращали HTML-строки прямо из View:

from django.http import HttpResponse

def home_view(request):
    name = "Алексей"
    # ❌ Смешивание логики и разметки:
    html = f"<html><body><h1>Привет, {name}!</h1></body></html>"
    return HttpResponse(html)

Минусы такого подхода:

  • Сложно писать и поддерживать сложную верстку.
  • Смешивается бизнес-логика (Python) и интерфейс (HTML).
  • Веб-дизайнер не может редактировать страницу без знания Python.
⚠️

Спагетти-код

Встраивание HTML в Python-строки делает проект хрупким и нечитаемым при росте приложения.

Решение: Паттерн MVT и Шаблоны

Django реализует архитектурную схему MVT (Model-View-Template). Это разновидность MVC, адаптированная под веб:

View (Представление)

Получает запрос, работает с базой данных (через Model), формирует контекст (данные) и вызывает шаблон.

Template (Шаблон)

HTML-файл со специальной разметкой, которая указывает, куда вставлять динамические данные из View.

Главный принцип: Разделение ответственности (Separation of Concerns). View отвечает за что отобразить (данные), а Template — за как отобразить (внешний вид).

Настройка шаблонов в settings.py

В файле настроек за конфигурацию отвечает список TEMPLATES:

TEMPLATES = [
    {
        'BACKEND': 'django.template.backends.django.DjangoTemplates',
        'DIRS': [BASE_DIR / 'templates'], # Глобальная папка шаблонов проекта
        'APP_DIRS': True,                 # Искать шаблоны внутри папок приложений
        'OPTIONS': {
            'context_processors': [ ... ],
        },
    },
]
  • DIRS: Django ищет шаблоны в указанных папках на уровне проекта (например, в корневой папке templates).
  • APP_DIRS: True: Автоматический поиск в папке templates/ каждого зарегистрированного в INSTALLED_APPS приложения.

Анатомия рендеринга: Функция render()

Для загрузки шаблона и наполнения его данными используется встроенная функция render():

from django.shortcuts import render

def home_view(request):
    # Данные для шаблона упаковываются в словарь context
    context = {
        'username': 'Алексей',
        'age': 16,
    }
    # Функция render объединяет request, путь к шаблону и данные
    return render(request, 'homepage.html', context)

Параметры функции render:

  1. request — исходный HTTP-запрос (обязательно).
  2. template_name — имя файла шаблона (путь относительно папки шаблонов).
  3. context — словарь с данными для вывода (необязательно, но почти всегда передается).

Контекст шаблона (Context Dictionary)

Контекст — это обычный Python-словарь (dict), ключи которого становятся переменными в HTML-файле шаблона:

# В файле views.py
context = {
    'title': 'Личный кабинет',
    'rating': 4.95,
    'tags': ['math', 'python', 'django']
}

В HTML-шаблоне:

  • title вернет строку "Личный кабинет"
  • rating вернет число 4.95
  • tags вернет список тегов

Что можно передавать?

  • Простые типы: str, int, float, bool.
  • Коллекции: list, dict, set, tuple.
  • Объекты классов (включая модели БД).
  • Функции и методы объектов.

Синтаксис шаблонов Django (DTL)

Для разметки HTML используется Django Template Language (DTL). У него есть четыре основных конструкции:

Синтаксис Название Назначение Пример
{{ variable }} Переменные Вывод значения на экран {{ username }}
{% tag %} Теги Логика: циклы, условия, блоки {% if age >= 18 %}
{{ var|filter }} Фильтры Преобразование вывода переменных {{ username|lower }}
{# comment #} Комментарии Скрытый от пользователя текст {# это комментарий #}

Вывод переменных

Двойные фигурные скобки заменяются на значение переменной в момент рендеринга:

<!-- Шаблон: profile.html -->
<div class="user-card">
    <h2>Пользователь: {{ username }}</h2>
    <p>Возраст: {{ age }} лет</p>
</div>

Результат сборки на сервере (то, что увидит браузер клиента):

<div class="user-card">
    <h2>Пользователь: Алексей</h2>
    <p>Возраст: 16 лет</p>
</div>
Если переменная отсутствует в словаре context, Django не вызывает ошибку! Вместо этого он молча выведет пустую строку (или значение, заданное настройкой string_if_invalid).

Обращение через точку (Dot Notation)

В DTL используется универсальный оператор точки для доступа к вложенным структурам. Django сам понимает, что нужно сделать:

  • Ключи словаря: {{ user.email }} → user['email']
  • Атрибуты объекта: {{ book.title }} → book.title
  • Методы объекта: {{ user.get_full_name }} → user.get_full_name()
    (Внимание: методы вызываются без круглых скобок и не должны принимать аргументы!)
  • Индексы списков: {{ participants.0 }} → participants[0]
    (Отрицательные индексы типа -1 не поддерживаются через точку)
Порядок поиска: если вы пишете foo.bar, Django пытается сделать: 1) foo['bar'], 2) foo.bar, 3) foo.bar(), 4) foo[bar] (если bar — индекс).

Фильтры шаблонов: Преобразование данных

Фильтры модифицируют отображение переменной. Они записываются через вертикальную черту |:

  • {{ name|upper }} — переведет в верхний регистр (АЛЕКСЕЙ).
  • {{ text|lower }} — переведет в нижний регистр.
  • {{ desc|default:"Описание отсутствует" }} — выведет текст по умолчанию, если переменная пуста или равна None.
  • {{ students|length }} — вернет количество элементов в списке.
  • {{ title|truncatewords:3 }} — обрежет строку до 3 слов и добавит многоточие.
  • {{ price|floatformat:2 }} — округлит число с плавающей точкой до 2 знаков после запятой.
  • {{ date|date:"Y-m-d" }} — отформатирует объект даты (например, 2026-06-29).
{# Можно комбинировать (цепочки фильтров): #}
<p>{{ user.get_full_name|upper|default:"ГОСТЬ" }}</p>

Безопасность и фильтр safe

По умолчанию Django автоматически экранирует все спецсимволы HTML (<, >, &, ', ") для защиты от XSS-атак (внедрения вредоносного JS-кода).

# views.py: context = {'comment': '<b>Привет</b>'}
# HTML: {{ comment }}
# В браузере отобразится как текст: <b>Привет</b>

Если вы уверены в безопасности HTML-кода и хотите отрендерить его как теги, используйте фильтр safe:

<p>Форматированный текст: {{ comment|safe }}</p>
<!-- Отобразится жирным: Привет -->

⚠️ Осторожно!

Никогда не применяйте фильтр safe к данным, которые ввел пользователь (комментарии, имена, отзывы). Это открывает уязвимость для межсайтового скриптинга (XSS).

Теги: Цикл {% for %}

Используется для перебора списков, кортежей или словарей в HTML:

<ul>
    {% for student in students %}
        <li>{{ forloop.counter }}. {{ student }}</li>
    {% empty %}
        <li>Список студентов пуст</li>
    {% endfor %}
</ul>

Ключевые фичи:

  • {% empty %} — блок, который выполнится, если список пуст или равен None.
  • forloop.counter — автоматическая переменная цикла, хранит индекс текущей итерации (начиная с 1).
  • forloop.counter0 (начиная с 0), forloop.first / forloop.last (булевы флаги).

Теги: Условие {% if %}

Условные операторы позволяют отображать элементы интерфейса выборочно:

{% if score >= 90 %}
    <div class="badge success">Отличный результат (A)!</div>
{% elif score >= 75 %}
    <div class="badge info">Хороший результат (B)</div>
{% else %}
    <div class="badge warning">Нужно потренироваться</div>
{% endif %}

Логические операторы в условиях DTL:

  • and, or, not (например, {% if user.is_authenticated and not user.is_staff %}).
  • Операторы сравнения: ==, !=, <, >, <=, >=.
  • Проверка вхождения: in, not in (например, {% if "admin" in user.groups %}).

Комментарии в DTL

Однострочные комментарии:

{# Это примечание не попадет в итоговый HTML #}
<p>Добро пожаловать!</p>

Многострочные комментарии:

{% comment "Комментарий для отладки" %}
    <div class="debug-info">
        <p>Этот блок полностью игнорируется Django.</p>
    </div>
{% endcomment %}

DTL против HTML комментариев

Обычные HTML комментарии вида <!-- ... --> передаются в браузер и видны пользователю при просмотре исходного кода страницы. Комментарии DTL обрабатываются на сервере и полностью вырезаются из итогового ответа.

Разделение логики и представления

Архитектурное правило хорошего тона при написании шаблонов:

Что НЕЛЬЗЯ делать в шаблоне:

  • Писать сложные вычисления или бизнес-логику.
  • Делать запросы к базе данных напрямую.
  • Вызывать тяжелые методы, изменяющие состояние БД.
  • Писать код, требующий передачи аргументов в функции.

Что НУЖНО делать во View:

  • Выполнить все фильтрации и вычисления на Python.
  • Получить готовые списки и объекты из БД.
  • Сформировать простой словарь контекста.
  • Передать подготовленные данные в шаблон для простой отрисовки.

Типичные ошибки разработчиков

  • TemplateDoesNotExist — Django не может найти файл шаблона. Проверьте:
    • Прописана ли папка в DIRS настроек settings.py?
    • Добавлено ли приложение в INSTALLED_APPS (если используется APP_DIRS: True)?
    • Правильно ли указаны регистр букв и расширение файла (.html)?
  • Пустые значения на экране — опечатка в имени переменной в HTML или в ключе словаря во View (например, {{ user_name }} вместо {{ username }}).
  • Попытка вызова метода со скобками — запись вида {{ user.get_full_name() }} вызовет синтаксическую ошибку DTL. Пишите: {{ user.get_full_name }}.

Практическая демонстрация

Мы создадим мини-проект «Динамическое табло ЛФМШ "Квант"»:

  1. Настроим единую папку templates/ в проекте.
  2. Создадим View, передающую сложный контекст:
    • Название лагеря и текущую дату.
    • Список учебных групп и количество участников.
    • Статус работы столовой (булев флаг).
    • Список объявлений дня.
  3. Напишем шаблон с использованием переменных, циклов, условий и встроенных фильтров.

Итоги урока

  • Шаблоны Django отделяют верстку (HTML) от кода управления (Python).
  • Функция render() связывает HTTP-запрос, HTML-шаблон и словарь контекста.
  • Контекст — словарь, ключи которого доступны в шаблоне как переменные.
  • DTL предоставляет синтаксис переменных ({{ }}), тегов ({% %}), фильтров (|) и комментариев ({# #}).
  • Через точку можно обращаться к ключам словаря, атрибутам, методам и индексам.
