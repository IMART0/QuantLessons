Проблема: Stateless HTTP

Протокол HTTP, на котором держится весь веб, является stateless (без сохранения состояния).

  • Каждый запрос от браузера к серверу обрабатывается «с чистого листа».
  • Сервер не помнит предыдущие запросы того же клиента.
  • Проблема: без дополнительных костылей мы бы разлогинивались после каждого перехода по ссылке, а корзина интернет-магазина обнулялась при обновлении страницы.
Аналогия:

Представьте врача с амнезией. Каждый раз, когда вы заходите в кабинет (делаете запрос), он видит вас впервые. Чтобы он вспомнил вас, вы должны каждый раз показывать ему медицинскую карту (передавать идентификатор).

Что такое Cookies (Куки)?

Cookies — это небольшие текстовые фрагменты данных, которые сервер отправляет в браузер клиента, а браузер сохраняет их локально и автоматически отправляет обратно с каждым последующим запросом к этому же серверу.

Схема работы:
  1. Браузер делает запрос: GET /index.html
  2. Сервер присылает ответ со специальным заголовком: Set-Cookie: user=Alex
  3. Браузер сохраняет этот файл у себя на диске.
  4. При следующем запросе браузер сам добавляет заголовок: Cookie: user=Alex. Теперь сервер знает, кто пришёл!

Структура Cookie и её атрибуты

Cookie — это не просто пара «ключ-значение». У неё есть важные служебные атрибуты:

  • Expires / Max-Age: время жизни куки. Без него кука удалится при закрытии браузера (сессионная кука).
  • Domain & Path: определяют, для каких сайтов и папок на сервере кука активна.
  • Secure: если включено, кука передается только по зашифрованному протоколу HTTPS.
  • HttpOnly: запрещает доступ к куке из JavaScript (защита от XSS-атак).
  • SameSite: управляет отправкой кук при переходах со сторонних сайтов (защита от CSRF-атак).

Cookies в Django: Чтение и запись

В Django чтение кук происходит через объект запроса, а запись — через объект ответа:

# Чтение куки во View
def read_cookie_view(request):
    username = request.COOKIES.get('username', 'Гость')
    return HttpResponse(f"Привет, {username}!")

# Запись куки во View
def set_cookie_view(request):
    response = HttpResponse("Кука установлена!")
    response.set_cookie('username', 'Alex', max_age=3600, httponly=True)
    return response

Обратите внимание: мы сначала создаем объект response, вызываем у него метод set_cookie() и только потом возвращаем.

Ограничения и недостатки Cookies

  • Лимит размера: один файл куки не может превышать 4 КБ. Навешать много данных не получится.
  • Уязвимость: данные кук хранятся на компьютере клиента. Пользователь может легко открыть консоль разработчика и вручную поменять значение (например, с role=user на role=admin).
  • Лишний трафик: куки летают туда-обратно с каждым HTTP-запросом (включая картинки, CSS, JS), засоряя сетевой канал.
Важное правило безопасности:

Никогда не храните в обычных куках важные, секретные или легко подделываемые данные (пароли, баланс кошелька, права доступа)!

Сессии (Sessions) — безопасное решение

Чтобы обойти ограничения кук, используют сессии. Идея проста: хранить все данные пользователя на стороне сервера, а клиенту отдавать лишь случайный уникальный ключ.

Принцип работы сессий:
  1. Пользователь логинится. Django генерирует длинную случайную строку (например, "abc123xyz") — Session Key.
  2. Django создает в своей базе данных запись, где ключ — "abc123xyz", а значение — JSON-словарь со всеми данными пользователя.
  3. Сервер отправляет клиенту куку с именем sessionid и значением "abc123xyz".
  4. При следующем запросе браузер присылает эту куку. Django находит в БД словарь по ключу "abc123xyz" и загружает его в память.

Сессии в Django под капотом

В Django механизм сессий включен по умолчанию через класс-посредник (middleware).

  • Сессионные данные по умолчанию хранятся в таблице базы данных django_session.
  • Имя куки, в которой хранится ключ сессии: sessionid.
  • Сами данные в БД хранятся в закодированном виде (Base64 + подпись), чтобы их нельзя было легко прочесть в сыром виде из базы данных.
Где еще можно хранить сессии? (меняется в settings.py):
В БД (по умолчанию), в кэше (Redis / Memcached), в файлах или непосредственно в зашифрованных куках на клиенте.

Работа с сессиями во View

В Django доступ к сессии осуществляется через словарь-подобный объект request.session:

def cart_add(request, item_id):
    # Получаем корзину из сессии или создаем пустой список, если её нет
    cart = request.session.get('cart', [])
    cart.append(item_id)
    
    # Сохраняем обратно в сессию
    request.session['cart'] = cart
    
    # Важно: если мы изменяем изменяемый объект (список, словарь) внутри сессии,
    # нужно явно сообщить Django о необходимости сохранения в БД:
    request.session.modified = True
    return HttpResponse("Товар добавлен!")

Сравнение Cookies и Sessions

Характеристика Cookies (Куки) Sessions (Сессии)
Где хранятся данные? На устройстве клиента (браузер) На сервере (БД, кэш или файлы)
Объем данных Ограничен (до 4 КБ на одну куку) Практически неограничен
Безопасность Низкая (клиент может подделать) Высокая (клиент видит только ключ)
Скорость работы Очень быстрая (нет обращений к БД) Зависит от хранилища (нужен запрос в БД)
Нагрузка на сеть Передаются целиком при каждом запросе Передается только короткий ID сессии

Идентификация, Аутентификация, Авторизация

Эти три термина часто путают, но они обозначают разные этапы входа в систему:

  • Идентификация — это заявление пользователя о том, кто он такой. Например, ввод логина или email: «Я пользователь с ником alex_99».
  • Аутентификация — это подтверждение личности. Пользователь доказывает, что он тот, за кого себя выдает (вводит пароль, код из SMS или прикладывает палец): «Вот мой пароль, проверьте».
  • Авторизация — это проверка прав доступа. Определение того, что именно этому пользователю разрешено делать на сайте: «У пользователя alex_99 есть права администратора, пустить его в админку».

Встроенная модель User в Django

В Django есть мощная готовая система пользователей (приложение django.contrib.auth). Модель User содержит следующие стандартные поля:

  • username — уникальное имя пользователя (логин).
  • email — адрес электронной почты.
  • password — хэшированное значение пароля.
  • first_name / last_name — имя и фамилия.
  • is_active — активен ли аккаунт (вместо удаления лучше делать False).
  • is_staff — разрешен ли доступ в панель администратора.
  • is_superuser — обладает ли всеми правами.
  • date_joined — дата регистрации.

Безопасность паролей и Хэширование

Золотое правило веб-разработки: никогда не храните пароли пользователей в открытом (чистом) виде в базе данных!

Если злоумышленник получит доступ к базе данных, он украдет пароли всех пользователей.

Для безопасности пароли прогоняют через односторонние криптографические хэш-функции. Обратно восстановить пароль из хэша невозможно.

Принцип хэша: 
Пароль: "qwerty" 
Hash: "sha256$53f2c...8a2b"

При авторизации сервер хэширует введенный пользователем пароль и сравнивает хэши. Если они совпали — пароль верный.

PBKDF2 Hashing в Django

Django использует продвинутый алгоритм хэширования PBKDF2 (по умолчанию с SHA-256).

  • Соль (Salt): случайная уникальная строка, которая добавляется к каждому паролю перед хэшированием. Это защищает от взлома по готовым таблицам хэшей (радужным таблицам).
  • Итерации: алгоритм выполняет хэширование сотни тысяч раз (в Django 5.0+ по умолчанию 600,000 итераций). Это делает процесс хэширования намеренно медленным, защищая от перебора паролей (брутфорса) на видеокартах.
Формат хранения в БД:
<algorithm>$<iterations>$<salt>$<hash>
pbkdf2_sha256$600000$AbCdEf123$xYz987...2B4c

Создание пользователей в коде

Для правильного хэширования паролей при создании пользователей ВСЕГДА используйте специальный метод create_user() менеджера модели:

from django.contrib.auth.models import User

# ПРАВИЛЬНО: пароль автоматически захэшируется
user = User.objects.create_user(
    username='ivan',
    email='ivan@mail.ru',
    password='SuperSafePassword123'
)

# НЕПРАВИЛЬНО: пароль запишется в БД в открытом виде, 
# и пользователь не сможет войти в аккаунт!
user = User.objects.create(username='ivan', password='plain_password')

Что такое Middleware?

Middleware (файлы-посредники) — это механизм фильтров, который встраивается в процесс обработки запроса и ответа в Django. Они выполняются последовательно для каждого входящего HTTP-запроса и исходящего HTTP-ответа.

Схема прохождения запроса:
Запрос от клиента → SecurityMiddleware → SessionMiddleware → AuthenticationMiddleware → Твоя View → (и обратно)

Через Middleware Django автоматически подтягивает сессии (request.session) и текущего пользователя (request.user) к каждому запросу до того, как запрос попадет во View.

Пример кастомного Middleware

Мы можем написать класс, который будет логировать каждый запрос в консоль:

class RequestLogMiddleware:
    def __init__(self, get_response):
        self.get_response = get_response

    def __call__(self, request):
        # Код, выполняемый ДО того, как View обработает запрос
        print(f"[LOG] Запрос {request.method} на адрес {request.path}")
        
        response = self.get_response(request)
        
        # Код, выполняемый ПОСЛЕ того, как View вернула ответ
        print(f"[LOG] Статус ответа: {response.status_code}")
        return response

Резюме и план практики

Ключевые выводы:

  1. Куки хранятся у клиента, сессии — на сервере (связаны через куку sessionid).
  2. Модель User хранит хэш пароля с солью с помощью алгоритма PBKDF2.
  3. Никогда не используйте User.objects.create() для пользователей. Только create_user()!
