Курс «Веб-разработка на Python (Django)»

Что такое деплой (Deployment)?

Деплой (развертывание) — это процесс переноса вашего веб-приложения с локального компьютера (разработка) на сервер (продакшен), где оно станет доступно пользователям со всего мира.

  • Локально (Development): DEBUG = True, SQLite, runserver. Всё работает быстро, ошибки видны на экране.
  • Сервер (Production): DEBUG = False, PostgreSQL, полноценные веб-серверы, защита от взлома, работа 24/7.

Главная цель

Обеспечить стабильную, быструю, безопасную работу сайта под высокими нагрузками и доступ по публичному доменному имени или IP-адресу.

Где разместить сайт? VPS/VDS vs Shared

Shared Хостинг (Общий)

Сотни сайтов делят ресурсы одного сервера. Доступны только базовые настройки (PHP, FTP).

❌ Не подходит для Python/Django из-за ограничений в установке системных библиотек и демонов.

VPS/VDS (Виртуальный сервер)

Вы получаете виртуальную машину с гарантированными ресурсами, собственным IP-адресом и полными правами администратора (root).

✅ Идеально для Django. Можно установить любую ОС (обычно Ubuntu), СУБД и Docker.

Анатомия классического продакшена

Как распределяются роли на реальном сервере:

1. Nginx

Внешний веб-сервер. Принимает запросы пользователей (HTTPS), раздает статические файлы напрямую, а динамические запросы пересылает дальше.

2. Gunicorn

WSGI-сервер приложений. Запускает несколько параллельных процессов Django, принимает запросы от Nginx и передает их в код Python.

3. Django

Бизнес-логика проекта. Обрабатывает URL, выполняет код представлений (views), общается с СУБД и возвращает HTML или JSON.

4. PostgreSQL

База данных. Надежное хранилище информации, оптимизированное для параллельных запросов и транзакций.

Настройки Django в settings.py для Production

# settings.py
# 1. ОБЯЗАТЕЛЬНО выключаем отладку. При True пользователи увидят пароли при ошибках!
DEBUG = False

# 2. Указываем доменные имена и IP-адреса, на которых разрешено работать сайту
ALLOWED_HOSTS = ['myproject.ru', '123.45.67.89', 'localhost', '127.0.0.1']

# 3. Секретный ключ должен быть сложным и храниться в тайне
SECRET_KEY = os.environ.get('DJANGO_SECRET_KEY', 'default-unsafe-key')

# 4. Список доверенных источников для отправки POST-запросов (защита CSRF)
CSRF_TRUSTED_ORIGINS = ['https://myproject.ru']
Важно: Никогда не оставляйте DEBUG = True на публичном сервере. Это самая частая причина утечки баз данных и секретных ключей!

Переменные окружения (.env)

Все секретные настройки (ключи, пароли БД, токены API) нельзя «хардкодить» в коде, чтобы они не попали в публичный репозиторий Git.

Файл .env (не коммитим!): 
DEBUG=False
SECRET_KEY=yoursecretkeyhere
DATABASE_URL=postgres://db_user:password@db:5432/db_name
Чтение в settings.py: 
import os
from dotenv import load_dotenv

load_dotenv() # Загружает переменные из .env

SECRET_KEY = os.getenv('SECRET_KEY')
DEBUG = os.getenv('DEBUG') == 'True'

Сбор статических файлов: collectstatic

При DEBUG = False встроенный сервер Django отключает раздачу картинок, CSS и JS. Эти файлы должен раздавать быстрый веб-сервер Nginx.

Настройка путей в settings.py: 
STATIC_URL = '/static/'
# Папка, куда Django соберет всю статику из всех приложений:
STATIC_ROOT = os.path.join(BASE_DIR, 'staticfiles')

Запуск сборки статики одной командой перед деплоем:

python manage.py collectstatic --noinput

Зачем это нужно?

Nginx написан на C и оптимизирован под отдачу файлов из файловой системы. Он делает это в тысячи раз быстрее и экономичнее, чем Python-код Django.

Gunicorn: WSGI сервер приложений

Django — это фреймворк, а не веб-сервер. Для его запуска в продакшене нужен WSGI-сервер, например, Gunicorn (Green Unicorn).

  • Многопоточность: Управляет пулом рабочих процессов (workers). Если один зависнет или выбросит ошибку, остальные продолжат обслуживать пользователей.
  • Оптимизация: Отлично держит постоянные соединения.
# Ручной запуск Gunicorn (слушает порт 8000)
gunicorn myproject.wsgi:application --bind 0.0.0.0:8000

Важно

Никогда не используйте python manage.py runserver на продакшене. Он однопоточный, медленный и падает при первой же перегрузке или ошибке.

Nginx: Обратный прокси (Reverse Proxy)

Пользователи отправляют запросы на стандартные порты 80 (HTTP) или 443 (HTTPS). На сервере их встречает Nginx.

  • Раздача статики: Запросы к /static/ и /media/ обрабатываются Nginx напрямую из папок на диске.
  • Проксирование: Запросы к динамическим страницам пересылаются на локальный порт Gunicorn (например, 127.0.0.1:8000 или Unix-сокет).
  • Безопасность: Скрывает структуру бэкенда, защищает от DDoS-атак, фильтрует плохие запросы.
  • SSL-сертификаты: Отвечает за шифрование трафика (HTTPS) с помощью Let's Encrypt.

Базовая конфигурация Nginx

# /etc/nginx/sites-available/myproject
server {
    listen 80;
    server_name myproject.ru 123.45.67.89;

    # Раздача статических файлов напрямую
    location /static/ {
        alias /home/django/myproject/staticfiles/;
    }

    # Проксирование всех остальных запросов на Gunicorn
    location / {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

Systemd: Автозапуск Gunicorn

Если сервер перезагрузится, Gunicorn должен запуститься автоматически. Для этого настраивают системную службу Systemd.

Файл службы: gunicorn.service 
[Unit]
Description=gunicorn daemon
After=network.target

[Service]
User=django
WorkingDirectory=/home/django/myproject
ExecStart=/home/django/venv/bin/gunicorn --workers 3 --bind 127.0.0.1:8000 myproject.wsgi:application

[Install]
WantedBy=multi-user.target
Управление службой в терминале: 
# Перезапустить службы
sudo systemctl daemon-reload

# Запустить и добавить в автозапуск
sudo systemctl start gunicorn
sudo systemctl enable gunicorn

# Статус работы
sudo systemctl status gunicorn

База данных в продакшене

Вместо файловой СУБД SQLite в продакшене используют клиент-серверную PostgreSQL.

  • Параллелизм: SQLite блокирует всю БД при записи. Если два пользователя одновременно пишут отзывы, один будет ждать. PostgreSQL поддерживает тысячи параллельных записей.
  • Надежность: Защита данных от сбоев питания, транзакции ACID, репликация.
# Требуется пакет psycopg2-binary
DATABASES = {
    'default': {
        'ENGINE': 'django.db.backends.postgresql',
        'NAME': 'my_db_name',
        'USER': 'my_db_user',
        'PASSWORD': 'strong_password_here',
        'HOST': 'localhost', # или IP контейнера
        'PORT': '5432',
    }
}

Миграция данных

При переходе на новую БД не забудьте накатить миграции:

python manage.py migrate

Перенести данные из SQLite можно через дамп:

python manage.py dumpdata > db.json

Что такое Docker и контейнеризация?

Контейнеризация упаковывает приложение и все его зависимости (Python, библиотеки, настройки ОС) в единый изолированный образ (Image).

  • Контейнер — запущенный экземпляр этого образа.
  • Решает проблему: «У меня на компьютере всё работает, а на сервере падает!». Контейнер работает абсолютно одинаково и на Windows, и на сервере Ubuntu.
  • Изоляция: Каждое приложение крутится в своей песочнице и не мешает другим.

Как это устроено

1. Создаем Dockerfile (рецепт сборки).
2. Собираем Docker Image (готовый слепок).
3. Запускаем Docker Container (работающее приложение).

Dockerfile для Django проекта

# 1. Базовый образ с установленным Python 3.12
FROM python:3.12-slim

# 2. Установка системных переменных (отключаем буферизацию вывода и .pyc файлы)
ENV PYTHONDONTWRITEBYTECODE=1
ENV PYTHONUNBUFFERED=1

# 3. Создаем и переходим в рабочую директорию внутри контейнера
WORKDIR /app

# 4. Копируем файл зависимостей и устанавливаем их
COPY requirements.txt /app/
RUN pip install --no-cache-dir -r requirements.txt

# 5. Копируем исходный код проекта в контейнер
COPY . /app/

# 6. Запускаем проект через Gunicorn на порту 8000
CMD ["gunicorn", "myproject.wsgi:application", "--bind", "0.0.0.0:8000"]

Docker Compose: Управление несколькими сервисами

Для запуска сайта нам нужны: Django, PostgreSQL, Nginx. Описывать их запуск вручную сложно. Docker Compose позволяет запустить всё одной командой из файла docker-compose.yml.

# docker-compose.yml
version: '3.8'

services:
  db:
    image: postgres:15
    environment:
      POSTGRES_DB: my_db
      POSTGRES_USER: user
      POSTGRES_PASSWORD: password
    volumes:
      - postgres_data:/var/lib/postgresql/data

  web:
    build: .
    command: gunicorn myproject.wsgi:application --bind 0.0.0.0:8000
    volumes:
      - .:/app
    ports:
      - "8000:8000"
    env_file:
      - .env
    depends_on:
      - db

volumes:
  postgres_data:

Основные команды Docker Compose

Запуск и сборка: 
# Собрать образы и запустить контейнеры
docker compose up --build

# Запустить в фоновом режиме (демоном)
docker compose up -d

# Остановить контейнеры
docker compose down

# Посмотреть логи запущенных сервисов
docker compose logs -f
Команды внутри контейнера:

Чтобы применить миграции или собрать статику внутри запущенного контейнера web:

# Применить миграции БД в контейнере
docker compose exec web python manage.py migrate

# Собрать статические файлы
docker compose exec web python manage.py collectstatic --noinput

# Создать суперпользователя
docker compose exec web python manage.py createsuperuser

Чек-лист перед деплоем проекта

  • Зависимости: Создан актуальный файл requirements.txt (с помощью команды pip freeze > requirements.txt).
  • Безопасность: DEBUG = False, SECRET_KEY скрыт в файле .env.
  • Статика: Настроены STATIC_ROOT и STATIC_URL для сбора статики.
  • БД: Настроено подключение к PostgreSQL вместо SQLite.
  • Хост: Прописаны домен сервера и IP в ALLOWED_HOSTS и CSRF_TRUSTED_ORIGINS.
  • Тесты: Все тесты проходят успешно на локальной машине.
Готовы? Сохраняем код в репозиторий, заходим на сервер по SSH и запускаем Docker Compose!

Резюме и переход к практике!

Мы сегодня узнали:

  • Деплой — перенос локального кода на VPS сервер.
  • В продакшене DEBUG должен быть False!
  • Nginx раздает статику и проксирует запросы на Gunicorn.
  • Секреты хранятся в .env файле, а не в коде.
  • Docker упаковывает код в изолированные контейнеры.
  • Docker Compose управляет запуском Django, Postgres и Nginx.

Давайте настроим проект для деплоя и упакуем его в Docker!
