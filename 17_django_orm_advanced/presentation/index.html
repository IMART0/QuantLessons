Реляционные связи: зачем разделять данные?

В реляционных СУБД данные не хранят «всё в одной куче». Процесс нормализации требует разделения информации по специализированным таблицам.

Почему дублирование — это зло?
Если в каждой строке книги хранить имя, биографию и email автора, то при изменении почты автора придётся обновить тысячи записей. Это ведёт к рассинхронизации данных и неэффективному использованию памяти.

Типы связей в базах данных:

  • Один-ко-многим (One-to-Many): У одного автора много книг.
  • Многие-ко-многим (Many-to-Many): У книги может быть несколько авторов, а у автора — много книг.
  • Один-к-одному (One-to-One): У одного пользователя ровно один профиль с настройками.

Связь один-ко-многим: ForeignKey

Используется, когда одна запись в таблице А связана с несколькими записями в таблице Б. В Django объявляется в той модели, которая относится к стороне «много».

class Author(models.Model):
    name = models.CharField(max_length=100)

class Book(models.Model):
    title = models.CharField(max_length=200)
    # Связываем книгу с автором
    author = models.ForeignKey(Author, on_delete=models.CASCADE, related_name='books')

Параметр on_delete (поведение при удалении родительской записи):

  • models.CASCADE — при удалении автора удаляются и все его книги.
  • models.SET_NULL — книги остаются, поле author зануляется (требует null=True).
  • models.PROTECT — запрещает удалять автора, пока на него ссылается хотя бы одна книга.

Связь многие-ко-многим: ManyToManyField

Используется, когда запись из таблицы А может быть связана со многими записями из Б, и наоборот (например, Книги и Жанры).

На уровне базы данных для этого создаётся скрытая промежуточная (связующая) таблица с парами внешних ключей.

Django полностью управляет промежуточной таблицей автоматически! 
class Genre(models.Model):
    name = models.CharField(max_length=50)

class Book(models.Model):
    title = models.CharField(max_length=200)
    genres = models.ManyToManyField(
        Genre, 
        related_name='books'
    )

Связь один-к-одному: OneToOneField

Аналогично ForeignKey, но с ограничением уникальности (unique=True): запись в таблице А может соответствовать строго одной записи в таблице Б.

from django.contrib.auth.models import User

class Profile(models.Model):
    # Каждому пользователю — строго один профиль
    user = models.OneToOneField(
        User, 
        on_delete=models.CASCADE, 
        related_name='profile'
    )
    avatar = models.ImageField(upload_to='avatars/')
    bio = models.TextField()
Обычно используется для расширения стандартной модели пользователей в Django пользовательскими полями без изменения исходного кода фреймворка.

Обратные связи и related_name

Прямой запрос: от Книги к Автору.
book.author — возвращает объект автора.

Обратный запрос: от Автора к Книгам.

  • По умолчанию: Django создаёт менеджер с именем [имя_модели]_set.
    author.book_set.all()
  • С параметром related_name='books':
    author.books.all() (гораздо красивее и понятнее!).
Важно: При определении связей всегда указывайте понятный related_name. Это стандарт профессиональной разработки! 
# Без related_name:
a.book_set.filter(price__gt=500)

# С related_name='books':
a.books.filter(price__gt=500)

Фильтрация по связанным полям

Django ORM позволяет делать запросы сквозь связи с помощью синтаксиса двойного подчёркивания (__).

# 1. Поиск книг, у автора которых имя "Лев Толстой"
books = Book.objects.filter(author__name='Лев Толстой')

# 2. Поиск авторов, написавших книги со словом "Python" в названии (обратная связь)
authors = Author.objects.filter(books__title__icontains='Python')

# 3. Поиск книг, у которых есть жанры с названием "Фантастика"
sci_fi_books = Book.objects.filter(genres__name='Фантастика')
ORM автоматически преобразует двойное подчёркивание в соответствующие SQL-операторы JOIN «под капотом».

Проблема N+1 запросов

Это одна из самых частых и опасных ошибок производительности при работе с ORM.

# Получаем список всех книг (1 запрос к БД)
books = Book.objects.all()

for book in books:
    # Для каждой книги запрашиваем имя автора (еще N запросов к БД!)
    print(f"Книга: {book.title}, Автор: {book.author.name}")
Если в базе данных 100 книг, этот код совершит 101 SQL-запрос (1 запрос на книги + 100 запросов на каждого автора отдельно). При высокой посещаемости сайта сервер базы данных просто откажет.

Почему ORM допускает это?

Django ORM работает по принципу «ленивой загрузки» (lazy loading). Данные запрашиваются из БД только тогда, когда к ним непосредственно обращаются.

  • При вызове Book.objects.all() Django берёт только данные о книгах.
  • Поля связей (например, внешние ключи) содержат только ID связанных записей.
  • При первом обращении к book.author.name ORM экстренно шлёт SQL-запрос: SELECT * FROM author WHERE id = ....
Решение: «Жадная загрузка» (eager loading). Нужно заставить ORM загрузить связанные данные сразу, в первом же запросе. Для этого в Django есть методы select_related и prefetch_related.

Оптимизация с select_related

Используется для связей ForeignKey и OneToOneField (одиночные связи на стороне «один»).

# Загружает книги и их авторов ОДНИМ запросом
books = Book.objects.select_related('author').all()

for book in books:
    # Данные автора уже лежат в памяти! Новых запросов нет.
    print(f"{book.title} — {book.author.name}")

Как это устроено внутри базы данных?
Django ORM генерирует SQL-запрос с оператором INNER JOIN или LEFT OUTER JOIN, склеивая таблицы прямо на стороне СУБД:

SELECT book.id, book.title, author.id, author.name 
FROM book 
INNER JOIN author ON (book.author_id = author.id);

Оптимизация с prefetch_related

Используется для связей ManyToManyField и обратных ForeignKey связей (где объектов может быть много).

# Загружает книги и связанные с ними жанры за 2 запроса!
books = Book.objects.prefetch_related('genres').all()

for book in books:
    for genre in book.genres.all():  # Данные уже в памяти, запросов нет!
        print(f"{book.title} — {genre.name}")

Как это работает?

  1. Первый запрос выбирает все книги.
  2. Второй запрос выбирает все жанры, которые привязаны к выбранным книгам (WHERE book_id IN (...)).
  3. Django в оперативной памяти склеивает эти объекты.

Агрегация данных: метод aggregate()

Агрегация — это вычисление какого-то итогового значения на основе всего набора данных (QuerySet).

Метод aggregate() «схлопывает» весь QuerySet в один обычный словарь Python. Получить объекты моделей после этого нельзя.

Функции агрегации импортируются из django.db.models: Count, Avg, Sum, Min, Max.

from django.db.models import Avg, Sum, Max, Min, Count

# Получим среднюю цену книг
result = Book.objects.aggregate(Avg('price'))
# Возвращает словарь: {'price__avg': 450.15}

Кастомные ключи и множественные агрегаты

Вы можете передавать свои имена ключей в словарь и вычислять несколько агрегатов одновременно:

stats = Book.objects.aggregate(
    average_price=Avg('price'),
    highest_price=Max('price'),
    lowest_price=Min('price'),
    total_books=Count('id')
)

print(f"Всего книг: {stats['total_books']}")
print(f"Диапазон цен: от {stats['lowest_price']} до {stats['highest_price']}")
# Выведет: {'average_price': 520.0, 'highest_price': 1200.0, ...}

Аннотация данных: метод annotate()

Аннотация — это добавление вычисляемого виртуального поля к каждому объекту QuerySet.

В отличие от aggregate(), метод annotate() возвращает полноценный QuerySet, в котором к каждому объекту привязано новое свойство.

Аналог в SQL — группировка строк (GROUP BY) с вычислением функций. 
# Добавим каждому автору 
# виртуальное поле books_count
authors = Author.objects.annotate(
    books_count=Count('books')
)

for author in authors:
    # books_count — виртуальное поле, 
    # вычисленное базой данных!
    print(author.name, author.books_count)

annotate() против aggregate(): Различия

aggregate()

  • Схлопывает QuerySet в словарь.
  • Служит для получения глобальных итогов (например, средняя цена всех товаров в магазине).
  • Результат: {'price__avg': 500}.

annotate()

  • Сохраняет QuerySet и добавляет атрибут к каждой строке.
  • Служит для получения пообъектной статистики (например, количество товаров в каждой категории).
  • Результат: <QuerySet [Category1, Category2]>.

Сложные аннотации и фильтрация

Результаты аннотации можно фильтровать с помощью метода filter() и сортировать через order_by().

# Найдём авторов, у которых более 5 книг, и отсортируем по продуктивности
prolific_authors = Author.objects.annotate(
    books_count=Count('books')
).filter(
    books_count__gt=5
).order_by(
    '-books_count'
)

# Фильтр ДО аннотации отсекает исходные записи.
# Фильтр ПОСЛЕ аннотации (как в примере) фильтрует сгруппированные результаты (HAVING в SQL).

Как увидеть реальный SQL-запрос?

Чтобы понять, сработала ли оптимизация select_related или нет, нужно заглянуть в сгенерированный SQL.

1. Свойство .query у QuerySet:

qs = Book.objects.all()
print(qs.query)
# Выведет сырой SQL-запрос в консоль

2. Логирование через Django settings.py:

LOGGING = {
    'version': 1,
    'loggers': {
        'django.db.backends': {
            'level': 'DEBUG',
            'handlers': ['console'],
        }
    }
}

Типичные ошибки при работе с ORM

  • Забытый select_related в циклах: приводит к падению сайта под нагрузкой из-за N+1 запросов.
  • Опечатки в названиях связей: использование точки . вместо двойного подчёркивания __ в фильтрах (правильно: book__author__name, а не book.author.name).
  • Неверная группировка фильтров: фильтрация по аннотируемому значению до того, как сама аннотация была объявлена в цепочке методов (вызывает ошибку FieldError).
  • Использование len(queryset) вместо queryset.count(): len() загружает ВСЕ объекты из базы данных в память, чтобы просто посчитать их число. count() выполняет быстрый SELECT COUNT(*).

Резюме и план практики

  • Используйте ForeignKey для отношений «один-ко-многим» и ManyToManyField для «многие-ко-многим».
  • Всегда указывайте related_name.
  • Боритесь с проблемой N+1 с помощью select_related (для одиночных связей) и prefetch_related (для множественных связей).
  • aggregate() — для одного числа по всей базе. annotate() — для добавления данных к каждому объекту.
