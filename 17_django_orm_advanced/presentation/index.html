Проект: Сайт летней школы «Квант»

В рамках единого проекта мы разрабатываем информационную систему лагеря. Нам нужно связать данные о пользователях, их ролях, расписании и личных достижениях.

Связанные сущности:
  • Участники и преподаватели: расширение стандартных пользователей.
  • Новости и мероприятия: привязка к авторам и спикерам.
  • Достижения (ачивки): система баллов и наград.

Чему мы научимся сегодня:

  • Проектировать связи моделей в Django.
  • Считать статистику прямо в СУБД (средний стаж, сумму баллов, количество наград).
  • Решать проблему N+1 и ускорять расписание лагеря в десятки раз.

Связь один-к-одному: OneToOneField

Используется, когда одна запись в таблице строго соответствует одной записи в другой таблице. Идеально для расширения стандартной модели User.

from django.contrib.auth.models import User
from django.db import models

class Teacher(models.Model):
    # У каждого преподавателя ровно один аккаунт User
    user = models.OneToOneField(User, on_delete=models.CASCADE, related_name='teacher_profile')
    experience = models.PositiveIntegerField(default=0, verbose_name="Стаж (лет)")
    subject = models.CharField(max_length=100, verbose_name="Предмет")

Параметр on_delete=models.CASCADE: при удалении пользователя User автоматически удалится его профиль преподавателя Teacher.

Связь один-ко-многим: ForeignKey

Используется, когда у одного объекта (например, автора) может быть много дочерних объектов (новостей, событий). Создается на стороне «много».

class News(models.Model):
    title = models.CharField(max_length=200, verbose_name="Заголовок")
    content = models.TextField(verbose_name="Текст")
    # У новости есть один автор, но автор может написать много новостей
    author = models.ForeignKey(User, on_delete=models.CASCADE, related_name='news')
    created_at = models.DateTimeField(auto_now_add=True)

Варианты удаления on_delete:

  • models.CASCADE — удалили автора → стерлись все его новости.
  • models.PROTECT — запрещает удалять автора, пока у него есть новости.
  • models.SET_NULL — обнуляет поле автора у новостей (требует null=True, blank=True).

Связь многие-ко-многим: ManyToManyField

Ученик лагеря может заработать множество достижений, а одно и то же достижение могут получить сотни учеников.

На уровне базы данных Django автоматически создаёт промежуточную таблицу со столбцами: user_id и achievement_id.

Методы управления связями:
user.achievements.add(achievement)
user.achievements.remove(achievement) 
class Achievement(models.Model):
    title = models.CharField(max_length=150)
    description = models.TextField()
    points = models.PositiveIntegerField(default=0)
    # Связываем достижение со многими пользователями
    users = models.ManyToManyField(
        User, 
        related_name='achievements'
    )

Обратные связи и параметр related_name

Связывая News с User напрямую через внешний ключ, мы получаем прямую ссылку: news.author.

Но как получить все новости пользователя? По умолчанию Django создает менеджер user.news_set.all().

С параметром related_name='news' мы можем использовать более естественный и понятный синтаксис: user.news.all().

Полезные примеры обратных связей:
  • user.teacher_profile ( OneToOneField )
  • user.news.all() ( ForeignKey )
  • user.achievements.all() ( ManyToManyField )

Фильтрация по связанным полям (Lookups)

Для фильтрации объектов по полям связанных моделей Django ORM использует синтаксис с двойным подчёркиванием (__).

# 1. Найти все новости, автором которых является администратор 'admin'
admin_news = News.objects.filter(author__username='admin')

# 2. Найти пользователей лагеря, у которых есть достижение 'Победитель олимпиады'
olympiad_winners = User.objects.filter(achievements__title='Победитель олимпиады')

# 3. Найти новости, написанные преподавателями физики
physics_news = News.objects.filter(author__teacher_profile__subject='Физика')

ORM автоматически сгенерирует SQL-запрос с оператором JOIN за вас.

Проблема N+1 запросов: Расписание лагеря

Представим, что мы выводим список мероприятий в расписании лагеря, отображая название и имя организатора:

# Выборка всех мероприятий (1 запрос к БД)
events = Event.objects.all()

# Вывод организаторов в цикле
for event in events:
    # Каждый шаг цикла делает НОВЫЙ запрос к таблице User для получения имени!
    print(f"Событие: {event.title} | Организатор: {event.creator.username}")
Если в расписании 50 мероприятий, Django сделает 1 + 50 = 51 запрос к базе данных. Это катастрофически снижает скорость работы сайта при росте базы!

Почему ORM «ленивая»?

Django ORM экономит память и не запрашивает связанные таблицы по умолчанию. В объекте Event изначально хранится только числовой creator_id.

Когда вы пишете event.creator.username, ORM понимает, что данных о пользователе в памяти нет, и делает точечный SQL-запрос.

Решение: «Жадная загрузка» (Eager Loading)
Мы должны заранее приказать Django ORM вытащить связанные объекты из базы данных за один или два запроса с помощью методов select_related и prefetch_related.

Решение: select_related (SQL JOIN)

Метод select_related используется для связей ForeignKey и OneToOneField (когда объект один). Он совершает SQL JOIN.

# Всего 1 SQL-запрос с объединением таблиц
events = Event.objects.select_related('creator').all()

for event in events:
    # Данные создателя уже загружены в оперативную память!
    print(f"Событие: {event.title} | Организатор: {event.creator.username}")

Как это выглядит в SQL под капотом:

SELECT event.*, user.* FROM event 
INNER JOIN auth_user ON (event.creator_id = auth_user.id);

Решение: prefetch_related (Дополнительный запрос)

Метод prefetch_related используется для связей ManyToManyField и обратных связей. Он делает отдельный запрос с оператором IN.

# Всего 2 SQL-запроса (первый — события, второй — спикеры)
events = Event.objects.prefetch_related('speakers').all()

for event in events:
    # Спикеры берутся из кэша в оперативной памяти Python
    speakers = ", ".join([s.username for s in event.speakers.all()])
    print(f"Событие: {event.title} | Спикеры: {speakers}")

Как это работает: Django выбирает все события, собирает ID их спикеров и запрашивает их одним запросом: SELECT * FROM auth_user WHERE id IN (1, 5, 12, ...);

Сравнение методов оптимизации

Характеристика select_related prefetch_related
Тип связи ForeignKey, OneToOneField (одиночные связи) ManyToManyField, обратные связи (множественные)
Как работает в БД SQL JOIN в одном запросе Дополнительный запрос с SELECT ... WHERE id IN (...)
Где склеивается На стороне СУБД На стороне Python в оперативной памяти
Количество запросов Всегда ровно 1 запрос Обычно 2 запроса (1 для главной, 1 для связанной таблицы)

Сложная оптимизация: Вложенные связи

А что если для каждого спикера (User) мероприятия нам нужно вывести его стаж преподавания из модели Teacher?

# Используем двойное подчёркивание для prefetch вложенных OneToOne связей!
events = Event.objects.prefetch_related('speakers__teacher_profile').all()

for event in events:
    print(f"Мероприятие: {event.title}")
    for speaker in event.speakers.all():
        # Обращаемся к профилю преподавателя без дополнительных запросов к БД!
        exp = speaker.teacher_profile.experience if hasattr(speaker, 'teacher_profile') else 0
        print(f" - Спикер: {speaker.username}, Опыт: {exp} лет")
Данная цепочка делает всего 3 запроса к БД (события, пользователи-спикеры, профили преподавателей) независимо от количества событий!

Агрегация данных: Метод aggregate()

Позволяет вычислять итоговые значения по всей таблице. Метод aggregate() возвращает словарь Python, прекращая цепочку QuerySet.

from django.db.models import Avg, Sum, Count, Max
from django.contrib.auth.models import User
from myapp.models import Teacher, Achievement

# 1. Найти средний опыт работы среди всех преподавателей лагеря
avg_exp = Teacher.objects.aggregate(average_experience=Avg('experience'))
# Результат: {'average_experience': 6.8}

# 2. Найти суммарный призовой фонд баллов всех существующих достижений
total_points = Achievement.objects.aggregate(points_sum=Sum('points'))
# Результат: {'points_sum': 1450}

Импортируйте функции агрегации из django.db.models.

Аннотация данных: Метод annotate()

Добавляет вычисляемые виртуальные поля к каждому объекту в QuerySet. Работает как SQL GROUP BY, сохраняя цепочку QuerySet.

# Для каждого пользователя считаем количество заработанных им достижений
users_with_achievements = User.objects.annotate(achievements_count=Count('achievements'))

for user in users_with_achievements:
    # У каждого объекта user появилось свойство achievements_count!
    print(f"Пользователь: {user.username} | Достижений: {user.achievements_count}")
Вычисление суммы баллов достижений для каждого пользователя:
users_with_points = User.objects.annotate(total_points=Sum('achievements__points'))

В чем разница? annotate() vs aggregate()

aggregate()

  • Масштаб: Глобальный итог по всей таблице.
  • Результат: Обычный словарь Python (dict).
  • Цепочка: Прерывает QuerySet (нельзя дописать .filter() или .order_by()).
Применяйте, когда нужна одна цифра на плашку.

annotate()

  • Масштаб: Пообъектные вычисления для каждой записи.
  • Результат: Объект QuerySet с новыми свойствами.
  • Цепочка: Сохраняет QuerySet (можно дальше сортировать, фильтровать).
Применяйте для вывода списков с внутренней статистикой.

Сложные аннотации и сортировка

Мы можем фильтровать и сортировать QuerySet, основываясь на вычисленных аннотациях:

# Получаем список пользователей, у которых сумма баллов больше 100,
# и сортируем их по убыванию баллов (Топ участников)
leaders = User.objects.annotate(
    total_points=Sum('achievements__points')
).filter(
    total_points__gt=100
).order_by('-total_points')

for leader in leaders:
    print(f"{leader.username}: {leader.total_points} баллов")

Порядок важен: фильтрация filter() после annotate() работает аналогично SQL-конструкции HAVING.

Профилирование и отладка SQL-запросов

Вы можете посмотреть сгенерированный SQL-запрос, распечатав свойство query у QuerySet:

qs = User.objects.filter(
    teacher_profile__experience__gt=5
)
print(qs.query)
Свойство .query есть только у объектов QuerySet. У результатов метода aggregate() его вызвать нельзя!

Для автоматического вывода всех SQL-запросов в консоль сервера добавьте логгер в settings.py:

LOGGING = {
    'version': 1,
    'handlers': {
        'console': {'class': 'logging.StreamHandler'},
    },
    'loggers': {
        'django.db.backends': {
            'level': 'DEBUG',
            'handlers': ['console'],
        }
    }
}

Резюме лекции

  • Три типа связей: OneToOneField, ForeignKey, ManyToManyField.
  • Параметр related_name делает обратные связи понятными.
  • Проблема N+1 запросов — враг производительности. Решается через select_related (одиночные связи) и prefetch_related (множественные связи).
  • Агрегаты (aggregate) рассчитывают статистику по всей таблице, возвращая словарь.
  • Аннотации (annotate) добавляют свойства каждому элементу QuerySet, сохраняя его.
  • Фильтрация с двойным подчёркиванием __ позволяет запрашивать данные через любые связи.
