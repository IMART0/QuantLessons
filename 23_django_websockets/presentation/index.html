Ограничения протокола HTTP

Стандартный протокол HTTP идеален для загрузки документов, но имеет ряд ограничений для интерактивных систем:

  • Request-Response: только клиент может инициировать обмен данными. Сервер не может отправить данные без запроса.
  • Соединение закрывается: после ответа TCP-соединение закрывается (или держится временно в Keep-Alive), заголовки передаются заново при каждом запросе.
  • Накладные расходы: отправка кук и заголовков (сотни байт) ради получения 2 байт данных.

Костыли прошлого:

  • Short Polling: клиент шлёт запросы каждые 2 секунды («Есть новые данные?»). 99% ответов — «Нет». Высокая нагрузка на CPU.
  • Long Polling: сервер держит запрос открытым, пока не появятся данные. Сложно масштабируется, занимает потоки сервера.

Протокол WebSocket

WebSocket — это протокол полнодуплексной (двунаправленной) связи поверх одного постоянного TCP-соединения.

  • Схема адресации: ws:// (незащищенный) и wss:// (защищенный, аналог HTTPS).
  • Соединение не закрывается: один раз установив связь, клиент и сервер могут слать друг другу сообщения в любой момент.
  • Минимальный оверхед: после рукопожатия фреймы данных передаются с заголовком всего в 2–10 байт.

Как создаётся соединение?

  1. Клиент шлёт обычный HTTP-запрос с заголовком Upgrade: websocket. Это называется Handshake (рукопожатие).
  2. Сервер соглашается, отправляя статус 101 Switching Protocols.
  3. HTTP-соединение трансформируется в WebSocket.

Сравнение HTTP и WebSocket

Характеристика HTTP (Hypertext Transfer Protocol) WebSocket (WS Protocol)
Тип связи Полудуплекс (только запрос-ответ) Полнодуплекс (одновременная отправка)
Инициатор Всегда только клиент И клиент, и сервер в любой момент
Жизнь соединения Короткая (запрос завершился — закрыли) Длинная (постоянное открытое соединение)
Нагрузка заголовков Большая (каждый раз Cookie, User-Agent) Минимальная (только при первом рукопожатии)
Примеры использования Просмотр статей, блогов, отправка форм Чаты, онлайн-игры, котировки, совместная работа

Синхронность vs Асинхронность

Синхронный подход (блокирующий)

Код выполняется строго последовательно. Если программа совершает сетевой запрос или читает файл с диска, выполнение блокируется. Процессор простаивает в ожидании ответа.

Чтобы обрабатывать параллельные запросы, приходится запускать много процессов или потоков ОС, что тратит оперативную память (каждый поток ~8 МБ).

Асинхронный подход (неблокирующий)

Если задача ожидает внешнее событие (I/O), управление временно передаётся другой задаче. Всё это работает на одном потоке в Event Loop (цикле событий).

Один процесс может удерживать тысячи одновременных открытых соединений WebSocket, тратя минимум памяти.

Асинхронность в Python

Начиная с версии 3.5, в Python встроена поддержка асинхронного программирования через модуль asyncio:

import asyncio

async def fetch_data(task_id, delay):
    print(f"Задача {task_id}: Начало ожидания...")
    await asyncio.sleep(delay)  # Неблокирующая пауза
    print(f"Задача {task_id}: Данные получены!")
    return {"id": task_id}

async def main():
    # Запускаем две корутины параллельно
    results = await asyncio.gather(fetch_data(1, 2.0), fetch_data(2, 1.0))
    print(f"Все результаты: {results}")

asyncio.run(main())

Интерфейсы серверов: WSGI vs ASGI

WSGI (Web Server Gateway Interface)

Создан в 2003 году. Синхронный стандарт взаимодействия Python-приложений с веб-серверами (Gunicorn, uWSGI).

  • Строгая схема: один запрос -> один ответ.
  • Не умеет работать с долгоживущими соединениями (WebSockets, Server-Sent Events).

ASGI (Asynchronous Server Gateway Interface)

Преемник WSGI. Позволяет асинхронным Python-приложениям работать со множеством протоколов.

  • Поддержка HTTP и WebSockets.
  • Многократный обмен сообщениями за время жизни одного соединения.
  • Серверы: Daphne, Uvicorn, Hypercorn.

Что такое Django Channels?

По умолчанию Django — это WSGI-фреймворк, ориентированный на синхронный HTTP.

Django Channels расширяет возможности Django, превращая его в асинхронный проект с поддержкой WebSockets, чатов, фоновых задач и многого другого.

Он заменяет стандартный запуск Django через WSGI на ASGI-режим.

Составные части Channels:

  • ASGI-сервер: (обычно Daphne или Uvicorn).
  • Consumers (Потребители): асинхронные контроллеры событий (аналог Views в Django).
  • Routing: маршрутизатор запросов по протоколам (HTTP/WS) и URL.
  • Channel Layers: система межпроцессного взаимодействия (обычно через Redis).

Потребители (Consumers) в Channels

Consumer (Потребитель) — базовый элемент Channels. Это класс, который обрабатывает события соединения (подключение, получение сообщения, отключение).

Синхронный (WebsocketConsumer)

  • Код пишется в обычном стиле без async/await.
  • Удобно, если нужно часто обращаться к синхронной ORM Django.
  • Под капотом запускается в отдельных потоках.

Асинхронный (AsyncWebsocketConsumer)

  • Использует async/await.
  • Максимальная производительность и эффективная утилизация ресурсов.
  • Для работы с БД требуются асинхронные обёртки.

События жизненного цикла WebSocket

Потребитель реагирует на 3 основных события. В асинхронном классе это выглядит так:

  • async def connect(self): — вызывается при попытке клиента установить соединение. Здесь мы должны вызвать await self.accept(), чтобы подтвердить рукопожатие, либо await self.close() для отклонения.
  • async def receive(self, text_data=None, bytes_data=None): — вызывается при получении сообщения от клиента. В text_data приходит строка (часто JSON).
  • async def disconnect(self, close_code): — вызывается, когда клиент закрывает вкладку, соединение рвётся из-за сети или сервер прерывает связь.

Маршрутизация запросов (Routing)

Вместо urls.py для WebSockets используется файл routing.py. Вместо path() используется re_path() или path() из Channels:

# chat/routing.py
from django.urls import path
from . import consumers

websocket_urlpatterns = [
    path("ws/chat//", consumers.ChatConsumer.as_asgi()),
]

В отличие от WSGI, где мы получаем объект request, в Channels в потребитель передаётся словарь scope (область видимости), содержащий параметры запроса, сессию, пользователя и параметры URL (self.scope['url_route']['kwargs']).

Настройка ASGI в проекте (asgi.py)

# myproject/asgi.py
import os
from channels.auth import AuthMiddlewareStack
from channels.routing import ProtocolTypeRouter, URLRouter
from django.core.asgi import get_asgi_application
import chat.routing

os.environ.setdefault('DJANGO_SETTINGS_MODULE', 'myproject.settings')

application = ProtocolTypeRouter({
    "http": get_asgi_application(), # Обычные HTTP-запросы
    "websocket": AuthMiddlewareStack( # Запросы WebSockets
        URLRouter(
            chat.routing.websocket_urlpatterns
        )
    ),
})

Channel Layers: Каналы и Группы

Channel Layer — это механизм, позволяющий разным инстансам потребителей (даже на разных серверах) общаться друг с другом.

  • Канал (Channel): индивидуальный почтовый ящик каждого потребителя (уникальное имя).
  • Группа (Group): чат-комната. Потребители могут вступать в группу и выходить из неё. Сообщение, отправленное в группу, получат ВСЕ её участники.

Redis как бэкенд

В продакшене для Channel Layers используется Redis — быстрое хранилище данных в памяти. Все запущенные процессы ASGI-сервера подключаются к Redis для мгновенной пересылки сообщений.

Пример: Эхо-потребитель (EchoConsumer)

Этот потребитель принимает любое сообщение от клиента и мгновенно возвращает его обратно:

# chat/consumers.py
import json
from channels.generic.websocket import AsyncWebsocketConsumer

class EchoConsumer(AsyncWebsocketConsumer):
    async def connect(self):
        await self.accept() # Разрешаем соединение

    async def receive(self, text_data):
        data = json.loads(text_data)
        message = data.get("message", "")
        
        # Отправляем сообщение обратно клиенту
        await self.send(text_data=json.dumps({
            "response": f"Эхо: {message}"
        }))

    async def disconnect(self, close_code):
        pass

Реальный чат: ChatConsumer c Группами

class ChatConsumer(AsyncWebsocketConsumer):
    async def connect(self):
        self.room_name = self.scope['url_route']['kwargs']['room_name']
        self.room_group_name = f"chat_{self.room_name}"

        # Присоединяемся к группе комнаты
        await self.channel_layer.group_add(self.room_group_name, self.channel_name)
        await self.accept()

    async def disconnect(self, close_code):
        # Покидаем группу
        await self.channel_layer.group_discard(self.room_group_name, self.channel_name)

    async def receive(self, text_data):
        data = json.loads(text_data)
        # Отправляем сообщение во ВСЮ группу
        await self.channel_layer.group_send(
            self.room_group_name,
            {"type": "chat.message", "message": data["message"]}
        )

    async def chat_message(self, event):
        # Этот метод срабатывает на событие группы с типом 'chat.message'
        await self.send(text_data=json.dumps({"message": event["message"]}))

WebSocket на клиенте (JavaScript)

В браузере встроен объект WebSocket. Нам не нужны сторонние библиотеки:

// Открываем соединение
const chatSocket = new WebSocket('ws://' + window.location.host + '/ws/chat/kvant/');

// Обрабатываем входящие сообщения
chatSocket.onmessage = function(e) {
    const data = JSON.parse(e.data);
    console.log("Новое сообщение:", data.message);
    document.querySelector('#chat-log').value += (data.message + '\n');
};

// Отправляем сообщение на сервер
function sendMessage(text) {
    chatSocket.send(JSON.stringify({
        'message': text
    }));
}

// Отслеживаем закрытие
chatSocket.onclose = function(e) { console.error('Соединение закрыто!'); };

Интеграция с Django ORM

Django ORM по умолчанию является синхронной. Вызов методов вроде MyModel.objects.create() внутри асинхронного метода заблокирует Event Loop или вызовет ошибку SynchronousOnlyOperation.

Способ 1: Асинхронные методы (Django 4.x+)

Используйте асинхронные аналоги методов ORM с приставкой a:

# Асинхронное создание записи
msg = await Message.objects.acreate(
    room=room,
    text=text,
    user=user
)

Способ 2: database_sync_to_async

Для сложных цепочек ORM или вызова методов моделей:

from channels.db import database_sync_to_async

@database_sync_to_async
def get_user_rooms(user):
    # Обычный синхронный код ORM
    return list(user.rooms.all())

Масштабирование и Деплой асинхронного Django

  • Разделение трафика: в продакшене HTTP-запросы обычно направляют на WSGI-сервер (Gunicorn), а WebSockets — на ASGI-сервер (Daphne/Uvicorn).
  • Настройка Nginx: Nginx должен уметь «проксировать» WebSocket-запросы. Для этого нужно настроить заголовки Upgrade и Connection.
  • Защита соединений (WSS): обязательно шифруйте трафик с помощью SSL-сертификатов (wss:// вместо ws://), иначе злоумышленники смогут перехватывать сообщения и красть сессии.
  • Redis: убедитесь, что Redis настроен на работу с паролем и находится в защищенной внутренней сети.

Частые ошибки при работе с Channels

  • Забыли вызвать await self.accept() в connect(): соединение будет бесконечно висеть в состоянии ожидания и сбросится клиентом по таймауту.
  • Блокировка Event Loop: вызов тяжелых синхронных функций (например, time.sleep() или requests.get()) внутри асинхронного метода. Сервер «зависает» для ВСЕХ подключенных пользователей. Используйте asyncio.sleep() и httpx.
  • Синхронный доступ к ORM: выполнение user.username, если объект user является ленивым (lazy-loaded). Это выбросит ошибку SynchronousOnlyOperation. Заранее подгружайте связанные сущности (select_related).
