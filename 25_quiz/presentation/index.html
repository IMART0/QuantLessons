HTML & CSS

Специфичность, блочная модель, семантика и флексы

Раунд 1: HTML & CSS (Вопросы 1-3)

Вопрос 1 (Специфичность): Какой цвет примет текст в блоке?
<div id="card" class="item primary" style="color: blue;">Текст</div>
div { color: red; }
#card { color: green; }
.item.primary { color: yellow; }
div.item { color: orange !important; }
Варианты: А) Синий | Б) Красный | В) Зеленый | Г) Оранжевый
Вопрос 2 (Блочная модель): Чему равна полная ширина элемента (без margin)?
.box {
  width: 300px; padding: 20px;
  border: 5px solid black; margin: 15px;
  box-sizing: content-box;
}
Варианты: А) 300px | Б) 340px | В) 350px | Г) 380px
Вопрос 3 (Семантика): Какой тег лучше всего подходит для независимого блока статьи или поста блога?
Варианты: А) <section> | Б) <article> | В) <div> | Г) <aside>

Раунд 1: HTML & CSS (Вопросы 4-5)

Вопрос 4 (Flexbox): Какое значение свойства flex-shrink применяется к флекс-элементам по умолчанию?
Варианты: А) 0 | Б) 1 | В) auto | Г) none
Вопрос 5 (Селекторы): Какие элементы будут выбраны селектором ul > li + li?
А) Все элементы списка li внутри ul.
Б) Только самый первый элемент списка li в ul.
В) Все элементы списка li, кроме первого.
Г) Только те элементы списка, которые содержат вложенные списки.

Ответы: Раунд 1 (HTML & CSS)

1. Г) Оранжевый. Правило !important перебивает любые другие уровни специфичности, включая инлайновые стили (style="...").

2. В) 350px. При box-sizing: content-box полная ширина = width (300) + padding-left/right (20+20) + border-left/right (5+5) = 350px. margin не входит в ширину самого элемента.

3. Б) <article>. Предназначен для автономного, самодостаточного контента, который можно переиспользовать независимо.

4. Б) 1. По умолчанию все флекс-элементы могут сжиматься, если контейнер слишком мал (flex-shrink: 1).

5. В) Все li, кроме первого. > выбирает прямых потомков, а соседний селектор + выбирает элемент li, идущий сразу за другим li. Самый первый li не идет после другого li, поэтому он отсекается.

Python & Web-протоколы

HTTP-методы, коды состояния, декораторы, сессии и cookie

Раунд 2: Python & Web-протоколы (Вопросы 1-3)

Вопрос 1 (HTTP методы): Какой из методов HTTP НЕ является идемпотентным согласно спецификации RFC 7231?
Варианты: А) GET | Б) PUT | В) POST | Г) DELETE
Вопрос 2 (Коды HTTP): Что означает статус-код 304 Not Modified?
А) Запрос был перенаправлен на несуществующую страницу.
Б) Ресурс не изменялся с момента последнего запроса, браузер может взять его из кэша.
В) У клиента нет прав на изменение этого ресурса.
Г) Сервер успешно внес изменения в базу данных.
Вопрос 3 (Декораторы): Что выведет этот код?
def decor(func):
    def wrapper():
        return func() + 2
    return wrapper

@decor
def get_num():
    return 5

print(get_num() * 2)
Варианты:
А) 14
Б) 12
В) 10
Г) TypeError

Раунд 2: Python & Web-протоколы (Вопросы 4-5)

Вопрос 4 (Cookie & Session): Где по умолчанию хранятся данные сессии в Django?
А) В локальном хранилище (LocalStorage) браузера пользователя.
Б) В куках (Cookies), отправляемых в браузер в зашифрованном виде.
В) В базе данных на сервере (таблица django_session).
Г) В оперативной памяти веб-сервера Gunicorn.
Вопрос 5 (Kwargs в URL): Каким будет словарь kwargs в Django-view при запросе к path('post/<int:pk>/', views.my_view) по пути /post/42/?
А) {'pk': 42}
Б) (42,)
В) {'request': request, 'pk': 42}
Г) Словарь будет пустым, а число попадет в args.

Ответы: Раунд 2 (Python & Web-протоколы)

1. В) POST. Идемпотентный метод при многократном повторении дает один и тот же результат. GET, PUT, DELETE — идемпотентны. Повторный POST создает новые записи (неидемпотентен).

2. Б) Ресурс не изменялся, берем из кэша. Это основа оптимизации трафика: сервер сообщает браузеру, что контент тот же, экономя время и трафик.

3. А) 14. Декоратор оборачивает функцию get_num, подменяя её на wrapper, который возвращает 5 + 2 = 7. При умножении на 2 получаем 14.

4. В) В базе данных на сервере (таблица django_session). В куках хранится только sessionid (уникальный ключ), по которому Django находит данные в БД.

5. А) {'pk': 42}. Все именованные параметры из пути URL передаются во view как именованные аргументы (keyword arguments / kwargs).

Ядро Django: Views, URLs, Templates

Архитектура MVT, CBV, контекстные процессоры и шаблоны

Раунд 3: Ядро Django (Вопросы 1-3)

Вопрос 1 (Архитектура MVT): Какая часть MVT-паттерна Django отвечает за обработку HTTP-запроса, извлечение данных и бизнес-логику?
Варианты: А) Model | Б) View | В) Template | Г) Controller
Вопрос 2 (URL роутинг): Какое правило совпадет с запросом /user/ivan/, но НЕ совпадет с /user/ivan/profile/?
А) path('user/<str:username>/profile/', views.profile)
Б) path('user/<str:username>', views.profile)
В) path('user/<str:username>/', views.profile)
Г) re_path(r'^user/(?P<username>\w+)', views.profile)
Вопрос 3 (Контекстные процессоры): В чем главная задача Context Processors в Django?
А) Очищать и валидировать данные пользователя перед обработкой во view.
Б) Добавлять определенные переменные во все шаблоны по умолчанию.
В) Собирать и компилировать статические файлы во время рендеринга.
Г) Оптимизировать SQL-запросы внутри шаблонов.

Раунд 3: Ядро Django (Вопросы 4-5)

Вопрос 4 (Шаблоны и экранирование): В Django-шаблоне выводится переменная {{ code }}. Что отобразится в браузере, если code = "<h1>Привет</h1>"?
А) Крупный заголовок первого уровня со словом "Привет".
Б) Текст <h1>Привет</h1> (теги отобразятся на экране как обычный текст).
В) Ошибка компиляции шаблона TemplateSyntaxError.
Г) Пустая строка (Django полностью удалит HTML-теги в целях безопасности).
Вопрос 5 (Теги и фильтры): В чем разница между тегами и фильтрами в шаблонах Django?
А) Фильтры обрабатывают данные из БД, а теги отвечают за стили CSS.
Б) Фильтры модифицируют вывод переменных ({{ var|filter }}), а теги реализуют логику ({% tag %}).
В) Фильтры выполняются в браузере с помощью JS, а теги — на сервере с помощью Python.
Г) Разницы нет, это синонимы для обозначения функций шаблонизатора.

Ответы: Раунд 3 (Ядро Django)

1. Б) View (Представление). Вопреки классическому MVC, где логику ведет Controller, в Django именно View принимает запросы и обрабатывает бизнес-логику (а роль контроллера выполняет сам фреймворк).

2. В) path('user/<str:username>/', ...). Метод path ищет точное совпадение строки с путями (с учетом слэшей). Вариант Г совпал бы с обоими адресами, так как не имеет символа конца строки $.

3. Б) Добавлять переменные во все шаблоны. Например, так в шаблонах всегда доступны request или user без явной передачи из views.

4. Б) Текст <h1>Привет</h1>. Django автоматически экранирует HTML, чтобы предотвратить XSS-атаки (выполнение вредоносного JS). Для рендера тегов нужен фильтр safe.

5. Б) Фильтры модифицируют переменные, теги реализуют логику. Фильтры пишутся через вертикальную черту, теги — в фигурных скобках с процентами.

Раунд 4

Django Models & ORM

Связи, ленивые запросы, миграции и оптимизации базы данных

Раунд 4: Django Models & ORM (Вопросы 1-3)

Вопрос 1 (Проблема N+1): В модели Book есть связь ForeignKey с моделью Author. Какая оптимизация спасет от N+1 запросов при рендере списка книг с авторами?
Варианты: А) prefetch_related | Б) select_related | В) defer | Г) filter(author__isnull=False)
Вопрос 2 (Связи): Что произойдет с книгами автора при его удалении, если поле модели описано как author = models.ForeignKey(Author, on_delete=models.PROTECT)?
А) Книги этого автора будут удалены автоматически.
Б) Поле author в книгах этого автора занулится (примет значение NULL).
В) Django выбросит ошибку ProtectedError и заблокирует удаление автора, пока у него есть книги.
Г) Автор удалится, а книги останутся с недействительной ссылкой.
Вопрос 3 (Миграции): Где Django хранит информацию о том, какие файлы миграций уже были запущены на базе данных?
Варианты: А) В settings.py | Б) В файлах кэша .pyc | В) В таблице БД django_migrations | Г) В файле .django_history

Раунд 4: Django Models & ORM (Вопросы 4-5)

Вопрос 4 (Ленивые QuerySet): Сколько запросов к БД будет сделано при выполнении этого кода?
books = Book.objects.filter(year__gt=2020)
active_books = books.filter(status='active')
first_book = active_books[0]
Варианты:
А) 3 запроса
Б) 2 запроса
В) 1 запрос
Г) 0 запросов
Вопрос 5 (Агрегация): Что вернет вызов Book.objects.aggregate(avg=Avg('rating'))?
А) QuerySet объектов Book с добавленным полем avg.
Б) Словарь Python вида {'avg': 4.5}.
В) Одно число с плавающей точкой (например, 4.5).
Г) Список авторов и их средних оценок.

Ответы: Раунд 4 (Django Models & ORM)

1. Б) select_related. Для связей «один-ко-многим» (ForeignKey) используется select_related, делающий SQL JOIN. prefetch_related используется для ManyToMany и обратных связей (делает отдельный SQL-запрос).

2. В) Заблокирует удаление автора (ProtectedError). Это защищает базу от потери логической целостности (не дает оставить книги без автора).

3. В) В специальной таблице django_migrations в самой базе данных. Django проверяет эту таблицу при запуске migrate.

4. В) 1 запрос. QuerySet в Django ленивы. Первые две строки только строят SQL-запрос. Запрос улетает в БД только на третьей строке при индексации (слайсинге [0], транслируемом в LIMIT 1).

5. Б) Словарь Python вида {'avg': 4.5}. В отличие от annotate(), которая дополняет каждый объект QuerySet, aggregate() сжимает весь QuerySet в одну строку данных и возвращает словарь.

Раунд 5

Архитектура, безопасность & деплой

Middleware, CSRF, SQL-инъекции, CORS и статика в продакшене

Раунд 5: Безопасность & Деплой (Вопросы 1-3)

Вопрос 1 (Middleware): В каком порядке Django обрабатывает список MIDDLEWARE при входящем запросе (Request)?
Варианты: А) Сверху вниз (от первого к последнему) | Б) Снизу вверх | В) В алфавитном порядке | Г) Одновременно
Вопрос 2 (CSRF защита): Как Django проверяет POST-запросы на защиту от CSRF-атак?
А) Сравнивает IP-адрес отправителя со списком доверенных хостов.
Б) Требует наличие уникального токена в теле POST-запроса и сверяет его с токеном из cookie.
В) Шифрует все передаваемые данные с помощью SSL/TLS ключа.
Г) Блокирует все запросы, пришедшие не из браузера Chrome.
Вопрос 3 (SQL-инъекции): Какой из вариантов кода в Django РИСКУЕТ получить SQL-инъекцию при передаче данных от пользователя user_input?
А) Book.objects.filter(title=user_input)
Б) Book.objects.raw("SELECT * FROM book WHERE title = %s", [user_input])
В) Book.objects.raw(f"SELECT * FROM book WHERE title = '{user_input}'")
Г) Book.objects.filter(title__contains=user_input)

Раунд 5: Безопасность & Деплой (Вопросы 4-5)

Вопрос 4 (CORS): Почему браузер блокирует React-приложение на localhost:3000 от чтения данных из Django API на localhost:8000 без настройки CORS?
А) Из-за ограничений базы данных Django на параллельные сессии.
Б) Из-за политики единого источника (Same-Origin Policy) в браузере.
В) Потому что Django не умеет работать по HTTP-протоколу с React.
Г) Потому что порт 3000 зарезервирован для баз данных.
Вопрос 5 (Деплой статики): Зачем нужна команда python manage.py collectstatic на сервере перед запуском сайта?
А) Чтобы сжать и минифицировать весь код CSS и JS.
Б) Чтобы скачать Bootstrap и jQuery файлы из внешних CDN.
В) Чтобы собрать статику всех приложений в одну папку STATIC_ROOT для раздачи веб-сервером (Nginx).
Г) Чтобы скомпилировать Python-код проекта в байт-код.

Ответы: Раунд 5 (Безопасность & Деплой)

1. А) Сверху вниз (от первого к последнему). Запрос идет по списку сверху вниз (Request), а возвращаемый ответ (Response) проходит обратно снизу вверх.

2. Б) Сверяет уникальный CSRF-токен из тела запроса с токеном из cookie. Для этого мы пишем тег {% csrf_token %} внутри форм.

3. В) Book.objects.raw(f"... '{user_input}'"). Прямое форматирование строк (f-строки) внедряет ввод пользователя в SQL-запрос напрямую, позволяя злоумышленнику сломать синтаксис и выполнить свой SQL-код. Варианты А, Б и Г безопасны, так как используют плейсхолдеры и экранирование ORM.

4. Б) Политика единого источника (Same-Origin Policy). Защищает данные: запрещает скриптам с одного сайта читать ответы от другого сайта, если тот явно не разрешил это через CORS-заголовки.

5. В) Чтобы собрать статику в одну общую папку STATIC_ROOT. В продакшене Django не должен раздавать статику сам (это медленно). Собранную статику напрямую и очень быстро раздает веб-сервер Nginx.

Бонус-раунд

Тай-брейк: Логика & Пазлы

Хитрые структуры данных, особенности ORM и загадки

Тай-брейк: Вопросы на логику

Вопрос 1 (Хеш-ключи): Чему равна длина словаря: len({1: 'a', 1.0: 'b', True: 'c'})?
Варианты: А) 3 | Б) 2 | В) 1 | Г) Вызов упадет с TypeError
Вопрос 2 (Загадка уникальности): В модели Django для поля прописано unique=True. Однако при тестировании разработчик смог сохранить дубликаты записей в базу без ошибок. Как это возможно?
А) SQLite не поддерживает ограничения уникальности в принципе.
Б) Не были созданы/применены миграции (БД не знает об ограничении), и записи создавались через Model.objects.create(), которая обходит валидацию самой модели Django.
В) Django отключает уникальность в тестовом режиме для экономии времени.
Г) Ограничение unique=True работает только в панели администратора Django.
Вопрос 3 (Загадка «Кто я?»): Кто я?
«Я стою между клиентом и Gunicorn. Я напрямую раздаю картинки и стили, сжимаю трафик и шифрую SSL. Как меня зовут?»
Варианты: А) SQLite | Б) Nginx | В) WSGI | Г) Git

Ответы: Тай-брейк

1. В) 1. В Python числа 1, 1.0 и логическое значение True равны между собой (1 == 1.0 == True) и имеют одинаковый хеш. Поскольку ключи словаря должны быть уникальными по значению и хешу, они перезаписывают один и тот же слот. Итоговый словарь: {1: 'c'}.

2. Б) Миграции не применили, а .create() обходит валидацию Django. Валидация уникальности на уровне Python-кода происходит в Django-формах или при явном вызове full_clean(). Метод ORM .create() сразу пытается сделать INSERT в БД. Так как миграции не применили, БД не знает об ограничении и сохраняет дубль.

3. Б) Nginx. Это классический веб-сервер и обратный прокси-сервер, который выполняет всю фронтенд-работу, разгружая Python-приложение.
