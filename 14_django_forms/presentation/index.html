Формы в Django

Создание, рендеринг, валидация данных и безопасность

Зачем нужны веб-формы?

Формы — основной способ получения данных от будущих участников и их родителей:

  • Регистрация школьников на летние смены лагеря
  • Отправка отзывов и предложений по работе кружков
  • Поиск по сайту (новости, мероприятия, расписание)
  • Подача заявок от вожатых и преподавателей

Проблемы ручного разбора POST-запросов:

  • Необходимость вручную писать HTML-код разметки <input>
  • Ручная проверка типов данных (строки, email, числа, даты)
  • Обеспечение безопасности (защита от XSS, CSRF-защита)

⚠️ Опасности ручного разбора

Разбор сырых данных из request.POST требует десятков строк проверок: if not email, try: int(age). Это ведёт к багам и уязвимостям безопасности.

💡 Подход Django

Django предоставляет декларативный класс forms.Form, который объединяет в себе генерацию HTML, очистку ввода, приведение типов и проверку ошибок.

Три ключевые задачи Django Forms

Класс forms.Form берет на себя рутину и автоматизирует три важных этапа работы с вводом:

1. Генерация HTML

Автоматически преобразует поля Python в HTML-элементы управления (<input>, <select>, <textarea>) с учетом нужных атрибутов и ошибок.

2. Валидация и очистка

Проверяет входящие данные на корректность и типы, удаляет лишние пробелы, приводит к Python-объектам (int, datetime, bool).

3. Вывод ошибок

Если пользователь ввел некорректные данные, форма вернет их обратно вместе с детальным описанием ошибок для каждого поля.

Объявление формы в коде

Создается файл forms.py внутри вашего приложения:

from django import forms

class CampContactForm(forms.Form):
    name = forms.CharField(label="Имя вожатого", max_length=100)
    email = forms.EmailField(label="Email для связи")
    message = forms.CharField(label="Сообщение", widget=forms.Textarea)
    counselor_experience = forms.IntegerField(label="Опыт работы (лет)", required=False)

Разбираем код:

  • Наследуемся от класса forms.Form
  • Каждый атрибут класса — это поле формы (объект Field)
  • Параметры полей (label, max_length, required) определяют валидацию и отображение

Основные типы полей (Form Fields)

Классы полей валидируют входящие строки и переводят их в Python-типы:

Класс поля HTML Элемент Результат валидации (Python-тип)
CharField <input type="text"> Строка (str)
EmailField <input type="email"> Строка (str) с проверкой формата email
IntegerField <input type="number"> Целое число (int)
BooleanField <input type="checkbox"> Логическое значение (bool)
ChoiceField <select> со списком <option> Выбранное строковое значение

Поля vs Виджеты (Fields vs Widgets)

Важно различать логику валидации и логику отрисовки:

  • Поле (Field) — отвечает за логику валидации и преобразование типов (например, EmailField проверяет формат email-адреса).
  • Виджет (Widget) — отвечает за HTML-представление на странице (например, виджет PasswordInput скрывает вводимые символы).

Пример переопределения виджета:

# Поле CharField, но отрисуется как пароль
password = forms.CharField(
    label="Пароль для личного кабинета",
    widget=forms.PasswordInput()
)

# Выбор даты с календарем
birth_date = forms.DateField(
    label="Дата рождения",
    widget=forms.DateInput(attrs={'type': 'date'})
)

Рендеринг формы в HTML-шаблоне

Django умеет рендерить форму целиком с помощью встроенных методов:

<form method="post">
    {% csrf_token %}
    {{ form.as_p }}
    <button type="submit">Отправить</button>
</form>

Методы быстрого вывода:

  • {{ form.as_p }} — поля оборачиваются в теги <p>
  • {{ form.as_table }} — поля выводятся в виде строк таблицы <tr>
  • {{ form.as_ul }} — поля оборачиваются в элементы списка <li>

🛡️ Важно: тег {% csrf_token %}

Внутри каждого HTML-шаблона с методом POST обязательно должен стоять тег {% csrf_token %}. Без него Django вернет ошибку 403 Forbidden! Это защита от межсайтовой подделки запросов (Cross-Site Request Forgery).

Ручная верстка полей формы

Для создания красивого дизайна (например, с Bootstrap) мы можем выводить поля по отдельности:

<form method="post">
    {% csrf_token %}
    <div class="form-group">
        <label for="{{ form.email.id_for_label }}">{{ form.email.label }}</label>
        {{ form.email }}  <!-- Сам input-элемент -->
        <span class="error">{{ form.email.errors }}</span>
    </div>
    <button type="submit" class="btn btn-primary">Отправить</button>
</form>

Полезные свойства полей в шаблоне:

  • {{ field.label }} — название поля.
  • {{ field.id_for_label }} — сгенерированный уникальный ID для тега <label>.
  • {{ field.errors }} — ошибки валидации, привязанные к этому полю.

Обработка формы во View (Контроллере)

Типичный паттерн обработки POST и GET запросов в Django:

from django.shortcuts import render
from .forms import CampContactForm

def feedback_view(request):
    if request.method == 'POST':
      # 1. Связанная форма (bound form) — наполняем данными из запроса
      form = CampContactForm(request.POST)
      if form.is_valid():  # 2. Проверка валидности
          # 3. Обработка чистых данных
          email = form.cleaned_data['email']
          # отправка письма, запись в БД и т.д.
          return render(request, 'success.html')
    else:
      # 1. Несвязанная форма (unbound form) — пустая для первого показа
      form = CampContactForm()
    
    return render(request, 'feedback.html', {'form': form})

Как работает метод is_valid()?

Метод form.is_valid() возвращает True, если форма связана с данными и не содержит ни одной ошибки:

  • Он запускает процесс валидации для всех полей.
  • Если ошибок нет, отфильтрованные данные помещаются в словарь form.cleaned_data.
  • Если ошибки найдены, словарь form.errors наполняется сообщениями, а is_valid() возвращает False.

📝 Важно: Состояния формы

  • Несвязанная (Unbound): Создана без данных (Form()). Свойство is_bound равно False. Валидация невозможна.
  • Связанная (Bound): Создана с данными (Form(request.POST)). Свойство is_bound равно True. Можно вызывать is_valid().

Очищенные данные: cleaned_data

После вызова is_valid() Django сохраняет преобразованные данные в form.cleaned_data.

Преобразование типов данных:

  • IntegerField преобразует строку "5" в число 5.
  • DateField преобразует "2026-07-02" в объект datetime.date.
  • BooleanField преобразует наличие чекбокса в True, отсутствие — в False.

⚠️ Ошибка KeyError!

Никогда не обращайтесь к cleaned_data до вызова is_valid() — словарь просто не будет существовать! Также помните, что если поле не прошло валидацию, его не будет в словаре cleaned_data.

Валидация отдельного поля (Field-level validation)

Если нужно добавить специфичную логику проверки для одного поля, определяют метод clean_<имя_поля>():

class CounselorRegistrationForm(forms.Form):
    username = forms.CharField(max_length=50)

    def clean_username(self):
        # 1. Получаем уже базово очищенное значение из self.cleaned_data
        username = self.cleaned_data['username']
        # 2. Наша кастомная проверка (не даем регистрировать админские имена)
        if "admin" in username.lower():
            raise forms.ValidationError("Имя пользователя не может содержать слово 'admin'!")
        # 3. ОБЯЗАТЕЛЬНО возвращаем проверенное значение!
        return username

Валидация нескольких полей (Form-level validation)

Если логика проверки зависит от комбинации нескольких полей (например, сравнение паролей для ЛК участника), переопределяют метод clean():

class ParticipantPasswordChangeForm(forms.Form):
    password = forms.CharField(widget=forms.PasswordInput)
    confirm_password = forms.CharField(widget=forms.PasswordInput)

    def clean(self):
        # 1. Запуск суперметода для сбора очищенных полей
        cleaned_data = super().clean()
        password = cleaned_data.get('password')
        confirm_password = cleaned_data.get('confirm_password')

        # 2. Проверка взаимосвязи полей
        if password and confirm_password and password != confirm_password:
            raise forms.ValidationError("Пароли для доступа к ЛК не совпадают!")
        
        # 3. Возвращаем весь cleaned_data
        return cleaned_data

Использование встроенных и кастомных валидаторов

Валидатор — это обычная функция или вызываемый объект, который принимает значение и выбрасывает ValidationError, если оно некорректно.

Их удобно переиспользовать в разных формах и моделях:

from django.core.validators import RegexValidator

phone_validator = RegexValidator(
    regex=r'^\+7\d{10}$',
    message="Телефон родителя должен быть в формате +71234567890"
)

Привязка валидатора к полю:

class ParentCallbackForm(forms.Form):
    parent_name = forms.CharField(label="ФИО родителя")
    phone = forms.CharField(
        label="Телефон для связи",
        validators=[phone_validator]
    )

Встроенные валидаторы: MinLengthValidator, MaxLengthValidator, MinValueValidator, EmailValidator.

Типичные ошибки начинающих разработчиков

  • Забыли написать return value в методе clean_<field>(). В таком случае поле возвращает None, затирая правильные данные в cleaned_data.
  • Забыли {% csrf_token %} в шаблоне. Приводит к падению формы с ошибкой 403 Forbidden.
  • Чтение cleaned_data без вызова is_valid(). Приведет к исключению AttributeError.
  • Попытка получить данные из cleaned_data при падении валидации. Если поле не прошло валидацию, в cleaned_data его ключа не будет. Всегда используйте безопасный метод .get().
