Напоминание: Архитектура MVT

Django работает по паттерну MVT (Model-View-Template):

  • Model (Модель): Данные и работа с БД.
  • Template (Шаблон): HTML-страница (внешний вид).
  • View (Представление): Мозг приложения. Связывает данные (Model) и внешний вид (Template).

Сегодня мы сфокусируемся на Views (Представлениях) и Маршрутизации (Routing).

Как это работает?

Пользователь переходит по URL-адресу → Django находит нужный View → View обрабатывает запрос → View возвращает ответ (HTML, JSON или ошибку).

Django-проект vs Django-приложение

В Django строго разделяются понятия Project (Проект) и Application (Приложение):

Project (Проект)

Это веб-сайт в целом. Содержит общие настройки всего сайта, подключение баз данных и глобальные маршруты (settings.py, urls.py).

Application (Приложение)

Это автономный модуль сайта, выполняющий конкретную задачу (например: блог, интернет-магазин, форум, личный кабинет).

Один проект может содержать множество независимых приложений!

Создание приложения (startapp)

Для создания нового приложения используется специальная команда CLI:

python manage.py startapp <название_приложения>

Например, создадим приложение для ведения блога posts:

python manage.py startapp posts
Важно: Название приложения должно быть в нижнем регистре, существительным во множественном числе (рекомендуется) и без пробелов/спецсимволов.

Анатомия Django-приложения

После запуска команды startapp создается папка со следующей структурой:

  • migrations/ — файлы миграций базы данных.
  • admin.py — регистрация моделей для админ-панели.
  • apps.py — конфигурация текущего приложения.
  • models.py — описание схем баз данных (Модели).
  • tests.py — юнит-тесты для тестирования кода.
  • views.py — представления (логика обработки запросов).
  • urls.py (создаем вручную) — маршруты приложения.

Регистрация приложения в settings.py

Django должен знать, какие приложения входят в проект. Их нужно прописать в списке INSTALLED_APPS в файле settings.py:

# mysite/settings.py

INSTALLED_APPS = [
    'django.contrib.admin',
    'django.contrib.auth',
    # ... другие системные приложения ...
    'posts.apps.PostsConfig', # Наш новый класс конфигурации
]
Частая ошибка: забыть добавить созданное приложение в INSTALLED_APPS. Без этого Django не увидит модели и шаблоны приложения.

Что такое View (Представление)?

View — это функция или класс, которые принимают HTTP-запрос от пользователя и возвращают HTTP-ответ.

Главное правило Django View:

Request (Запрос) → View (Логика) → Response (Ответ)

Если View принимает HTTP-запрос, она обязана вернуть объект HTTP-ответа (например, HTML-код, JSON, редирект или ошибку). Иначе Django выбросит ошибку ValueError.

Написание первой View (FBV)

Будем использовать Function-Based View (FBV) — представления на основе функций:

# posts/views.py
from django.http import HttpResponse

def index(request):
    return HttpResponse("Привет! Это главная страница блога.")
  • request — обязательный первый аргумент функции, содержащий данные об HTTP-запросе (заголовки, метод GET/POST, IP-адрес клиента).
  • HttpResponse — класс, который оборачивает строку в полноценный HTTP-ответ со статусом 200 OK.

Маршрутизация (Routing) в Django

Как Django узнает, какую функцию-view вызвать при переходе на конкретную страницу? Для этого используется файл urls.py.

  • URL Dispatcher — сопоставляет URL-адрес из адресной строки браузера со списком маршрутов.
  • При совпадении вызывается привязанная функция-view.
  • Маршруты описываются в списке urlpatterns с помощью функции path().
# Пример функции path()
path(route, view, name=None)
  • route: строка-шаблон пути (например, 'about/').
  • view: ссылка на функцию (например, views.index).
  • name: имя маршрута (для обратного поиска).

Делегирование маршрутов (include)

Глобальный файл urls.py проекта не должен содержать все маршруты! Мы должны делегировать их каждому приложению с помощью include:

# mysite/urls.py (Проект)
from django.contrib import admin
from django.urls import path, include

urlpatterns = [
    path('admin/', admin.site.urls),
    path('blog/', include('posts.urls')), # Все запросы к blog/ уходят в posts.urls
]
Функция include() позволяет подключать локальные файлы маршрутов приложений. Это делает проект модульным и чистым.

Создание локальных маршрутов (urls.py)

Создадим локальный файл urls.py внутри папки приложения posts/:

# posts/urls.py (Приложение)
from django.urls import path
from . import views # Импортируем представления из текущей папки

urlpatterns = [
    path('', views.index, name='index'), # Будет доступен по адресу blog/
]
Поскольку в проекте мы подключили маршруты приложения через path('blog/', include('posts.urls')), пустой путь '' в приложении превратится во внешний URL-адрес /blog/.

Схема обработки запроса в Django

Браузер (запрос /blog/)
  ↓
Django (проверяет корневой urls.py проекта)
  ↓ совпадение с 'blog/' → include('posts.urls')
Django (проверяет posts/urls.py)
  ↓ совпадение с '' → вызывает views.index(request)
Выполнение views.index() → return HttpResponse("Привет!")
  ↓
Браузер получает ответ (200 OK) и отображает текст

Динамическая маршрутизация

Что если нам нужны страницы для конкретных статей блога? Например, blog/post/1/, blog/post/2/.

Писать отдельный path для каждого ID невозможно. Мы используем угловые скобки для захвата переменных из URL:

# posts/urls.py
urlpatterns = [
    # ...
    path('post/<int:post_id>/', views.post_detail, name='post_detail'),
]
  • int — конвертер типа (параметр должен быть целым числом).
  • post_id — имя переменной, которая будет передана в функцию-view.

Стандартные конвертеры путей

Django предоставляет 5 встроенных конвертеров:

Конвертер Описание Пример соответствия
<int:...> Соответствует любому целому числу (0, 1, 42). blog/post/42/
<str:...> Любая непустая строка без косой черты / (по умолчанию). blog/category/it/
<slug:...> Буквы, цифры, дефисы и подчеркивания. blog/post/my-first-post/
<uuid:...> UUID-идентификатор. post/3f2b4.../
<path:...> Любая строка, включая слеши / (осторожно с этим!). files/docs/manual.pdf

Обработка динамических параметров во View

Имя переменной из urls.py должно строго совпадать с именем аргумента в функции-view:

# posts/views.py

# Маршрут: path('post/<int:post_id>/', views.post_detail)
def post_detail(request, post_id):
    # post_id автоматически придет как тип int благодаря конвертеру
    return HttpResponse(f"Вы читаете статью с ID: {post_id}")
Благодаря конвертеру int, переменная post_id внутри функции уже является числом (int), а не строкой! Приведение типов происходит под капотом.

Управление HTTP-статусами ответов

По умолчанию HttpResponse отправляет статус 200 OK. Мы можем вернуть другие статусы:

# 1. Изменение статуса через аргумент status
def error_view(request):
    return HttpResponse("Ресурс не найден", status=404)

# 2. Использование готовых подклассов HttpResponse
from django.http import HttpResponseNotFound, HttpResponseForbidden

def archive(request, year):
    if year > 2026:
        return HttpResponseNotFound("Архив за этот год еще не создан")
    return HttpResponse(f"Архив публикаций за {year} год")

Вызов ошибки 404 через исключения

Часто в логике приложения проще выбросить исключение (exception), чем возвращать объект ответа. Django предоставляет класс Http404:

from django.http import Http404

# Имитация базы данных постов
POSTS = {1: "Первый пост", 2: "Второй пост"}

def get_post(request, post_id):
    if post_id not in POSTS:
        raise Http404("Такого поста нет в базе данных")
    return HttpResponse(POSTS[post_id])
Внимание: Http404 — это исключение, поэтому его нужно выбрасывать с помощью ключевого слова raise, а не return!

Типичные ошибки при работе с View и URL

  • Забыли вернуть HttpResponse:
    Ошибка: "The view ... didn't return an HttpResponse object.". Всегда используйте return HttpResponse(...).
  • Несовпадение имен аргументов:
    В URL: <int:id>, во View: def detail(request, post_id). Имена должны совпадать!
  • Отсутствие завершающего слеша:
    Django по умолчанию перенаправляет с /about на /about/. Всегда пишите слеш в путях: path('about/', ...).
  • Забыли запятую:
    В списке urlpatterns каждый path() должен завершаться запятой!

Best Practices

  • Именуйте маршруты (name):
    Используйте осмысленные имена для путей, например name='post-detail'. Это позволит не хардкодить ссылки в будущем.
  • Модульность:
    Каждому приложению — свой urls.py. Главный urls.py проекта только координирует их через include().
  • Тонкие представления (Thin Views):
    В представлениях должна быть только логика обработки запроса и выбора ответа. Сложная бизнес-логика должна лежать в моделях.
  • Используйте правильные конвертеры:
    Не принимайте числовые ID в виде строк <str:id>, всегда используйте <int:id>.

Резюме и практические задания

  • startapp: создает обособленное Django-приложение.
  • INSTALLED_APPS: место регистрации приложения.
  • View: функция, принимающая request и возвращающая response.
  • include: перенаправляет маршруты в приложение.
  • Конвертеры путей: фильтруют и приводят типы URL-параметров.
  • Статус-коды: явно передают результат клиенту.
