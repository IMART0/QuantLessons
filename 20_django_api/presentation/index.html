Что такое API?

API (Application Programming Interface) — это интерфейс программирования приложений, контракт, позволяющий одной программе взаимодействовать с другой.

  • Обычный интерфейс (UI): для человека (кнопки, формы, страницы).
  • API-интерфейс: для программ и кода (функции, запросы, структуры данных).

В веб-разработке под API обычно понимают Web API — набор URL-адресов, по которым программы обмениваются данными по протоколу HTTP.

Аналогия: Ресторан

Вы — Клиент (браузер). Меню ресторана — это API (список доступных запросов). Официант — это HTTP-запрос, который несёт ваш заказ на кухню. Кухня — это Сервер, который готовит блюдо (данные) и отправляет его обратно.

Зачем веб-сайтам нужно API?

  • Разделение Frontend и Backend: сервер занимается только логикой и данными (Django), а интерфейс (React, Vue, iOS/Android) отрисовывается на клиенте.
  • Одно Backend-приложение для всех: один сервер обслуживает и сайт, и мобильное приложение, и умные часы.
  • Интеграция сторонних сервисов: получение погоды, оплата картой, авторизация через Telegram/VK.

Эволюция веб-приложений

Раньше: Django рендерил HTML-шаблон и отправлял его целиком (MVT).
Сейчас: Django принимает JSON, обрабатывает его и возвращает JSON. Клиент сам решает, как отобразить эти данные.

REST — архитектурный стиль

REST (Representational State Transfer) — это стиль архитектуры программного обеспечения для распределенных систем, созданный Роем Филдингом в 2000 году.

API, разработанное с соблюдением принципов REST, называется RESTful API.

Главная концепция: Ресурс (Resource)

В REST всё является ресурсом (пользователь, статья, бронирование). Каждый ресурс имеет уникальный адрес (URI). Например: /api/students/ (коллекция студентов) или /api/students/5/ (конкретный студент с ID = 5).

6 архитектурных ограничений REST

  1. Клиент-Сервер (Client-Server): чёткое разделение интерфейса (клиент) и хранения данных (сервер).
  2. Отсутствие состояния (Stateless): сервер не хранит контекст о сессии клиента. Каждый запрос должен содержать ВСЮ информацию для его выполнения.
  3. Кэширование (Cacheable): ответы сервера должны иметь пометку, можно ли их кэшировать, для снижения нагрузки.
  4. Единообразие интерфейса (Uniform Interface): одинаковый формат адресов, использование стандартных HTTP-методов (GET, POST и др.) и JSON.
  5. Слоистая система (Layered System): клиент не должен знать, общается он напрямую с сервером или через промежуточные узлы (прокси, балансировщики).
  6. Код по запросу (Code on Demand - необязательно): сервер может отправлять клиенту исполняемый код (например, JS-скрипты).

Формат JSON

JSON (JavaScript Object Notation) — текстовый формат обмена данными, основанный на подмножестве синтаксиса JavaScript.

  • Легко читается людьми и программами.
  • Является языконезависимым (поддерживается всеми современными языками).
  • Практически вытеснил старый формат XML в веб-разработке.
{
  "name": "Иван Сидоров",
  "age": 15,
  "is_active": true,
  "hobbies": ["робототехника", "физика"],
  "project": null
}

Сериализация и десериализация в Python

  • Сериализация (Serialization): перевод структуры данных из памяти программы (переменные, словари, объекты) в текстовую строку JSON для отправки по сети.
  • Десериализация (Deserialization): восстановление структуры данных из текстовой строки JSON в объекты языка (словари, списки, числа).
import json

# Сериализация (dict -> str)
data = {"name": "Анна", "grade": 9}
json_string = json.dumps(data, ensure_ascii=False)  # '{"name": "Анна", "grade": 9}'

# Десериализация (str -> dict)
parsed_data = json.loads(json_string)  # {"name": "Анна", "grade": 9}

Django и JSON: класс JsonResponse

Для возврата JSON-ответов Django предоставляет класс JsonResponse (наследник HttpResponse):

from django.http import JsonResponse

def info_view(request):
    data = {
        "camp_name": "Квант",
        "lesson": 20,
        "topics": ["API", "JSON", "REST"]
    }
    return JsonResponse(data)

Что происходит под капотом: JsonResponse автоматически сериализует переданный словарь в JSON-строку с помощью встроенного модуля json и устанавливает HTTP-заголовок Content-Type: application/json.

Возврат списков и параметр safe

По умолчанию JsonResponse ожидает на вход словарь (dict). Это сделано из соображений безопасности (старая уязвимость ECMAScript 5, связанная с перезаписью конструктора массива).

Если вы хотите передать список (например, массив объектов) или другой сериализуемый объект верхнего уровня, установите параметр safe=False:

from django.http import JsonResponse

def student_list_api(request):
    students = ["Миша", "Лена", "Саша"]
    # Без safe=False будет ошибка TypeError!
    return JsonResponse(students, safe=False)

Сериализация моделей Django вручную

Напрямую передать объект модели Django (например, из QuerySet) в JsonResponse нельзя, так как python-модуль json не знает, как преобразовывать сложные классы баз данных в текст. Мы должны перевести их в словари вручную:

from django.http import JsonResponse
from .models import Participant

def participant_list_api(request):
    participants = Participant.objects.all()
    # Преобразуем QuerySet в список словарей
    data = []
    for p in participants:
        data.append({
            "id": p.id,
            "name": p.name,
            "age": p.age,
            "project_title": p.project_title
        })
    return JsonResponse(data, safe=False)

CRUD и HTTP-методы в REST API

В REST API действия над ресурсами определяются HTTP-методом запроса:

Действие (CRUD) HTTP-метод Маршрут (URI) Ожидаемый статус ответа
Create (Создать) POST /api/students/ 201 Created
Read (Прочитать список) GET /api/students/ 200 OK
Read (Прочитать один) GET /api/students/<int:pk>/ 200 OK / 404 Not Found
Update (Обновить) PUT / PATCH /api/students/<int:pk>/ 200 OK / 400 Bad Request
Delete (Удалить) DELETE /api/students/<int:pk>/ 204 No Content

GET: Чтение и фильтрация параметров

Мы можем фильтровать результаты GET-запросов с помощью query-параметров (строки запроса): /api/participants/?age=15

def participant_list_api(request):
    queryset = Participant.objects.all()
    
    # Извлекаем query-параметр ?age= из URL
    age_filter = request.GET.get('age')
    if age_filter:
        queryset = queryset.filter(age=age_filter)
        
    data = [{"id": p.id, "name": p.name, "age": p.age} for p in queryset]
    return JsonResponse(data, safe=False)

Прием JSON-данных в POST-запросе

Для создания объектов клиент присылает JSON-данные в теле запроса (Request Body). Чтобы их прочитать в Django, нам нужно получить сырые байты из request.body и десериализовать их:

import json
from django.views.decorators.csrf import csrf_exempt

@csrf_exempt  # Отключаем CSRF-защиту для API-запросов
def create_participant_api(request):
    if request.method == 'POST':
        # Десериализуем байты тела запроса в словарь Python
        data = json.loads(request.body)
        
        name = data.get('name')
        age = data.get('age')
        
        # ... создание объекта в БД ...

Валидация данных в REST API

API должно строго проверять входные данные и возвращать понятные ошибки в формате JSON со статусом 400 Bad Request:

        # Валидация
        errors = {}
        if not name:
            errors['name'] = 'Это поле обязательно.'
        if age is None or not isinstance(age, int) or age <= 0:
            errors['age'] = 'Возраст должен быть положительным числом.'
            
        if errors:
            return JsonResponse({"errors": errors}, status=400)
            
        # Если всё верно, сохраняем в БД
        participant = Participant.objects.create(name=name, age=age)
        return JsonResponse({"id": participant.id, "name": participant.name}, status=201)

PUT и PATCH: Обновление данных

  • PUT: полная замена ресурса (клиент должен прислать все поля).
  • PATCH: частичное обновление (клиент присылает только те поля, которые хочет изменить).
# Фрагмент PATCH-запроса
data = json.loads(request.body)
participant = Participant.objects.filter(pk=pk).first()

if 'name' in data:
    participant.name = data['name']
if 'age' in data:
    participant.age = data['age']
    
participant.save()
return JsonResponse({"id": participant.id, "name": participant.name, "age": participant.age})

DELETE: Удаление ресурса

Для удаления ресурса отправляется HTTP-запрос DELETE на URI конкретного объекта. При успешном удалении REST-конвенция предписывает возвращать пустой ответ со статус-кодом 204 No Content:

@csrf_exempt
def delete_participant_api(request, pk):
    if request.method == 'DELETE':
        participant = Participant.objects.filter(pk=pk).first()
        if not participant:
            return JsonResponse({"error": "Участник не найден"}, status=404)
            
        participant.delete()
        # Возвращаем пустой ответ (status=204)
        return HttpResponse(status=204)

*Примечание: HttpResponse(status=204) возвращает пустой HTTP-пакет без тела, так как контент отсутствует.

Объединение CRUD в одной View

Обычно в Django при ручном написании API маршруты разделяют на два типа:

1. Работа со списком (Collection)

URL: /api/participants/

  • GET — список всех объектов.
  • POST — создание нового объекта.

2. Работа с элементом (Item)

URL: /api/participants/<int:pk>/

  • GET — детальная информация.
  • PUT/PATCH — обновление.
  • DELETE — удаление.

Внутри View мы просто делаем ветвление по if request.method == '...'.

Частые ошибки при написании API

  • Ошибка 403 Forbidden (CSRF Failed): Django по умолчанию блокирует POST/PUT/DELETE запросы без CSRF-токена. Для API-представлений необходимо отключать эту проверку через декоратор @csrf_exempt.
  • json.decoder.JSONDecodeError: возникает, если клиент прислал пустое тело запроса или невалидный JSON (например, забыл закрыть скобку). Код должен оборачивать json.loads() в блок try/except.
  • Игнорирование safe=False: попытка вернуть список через JsonResponse([...]) без указания именованного аргумента safe=False приводит к TypeError.
  • Неправильные статус-коды: возвращение 200 OK при ошибках валидации вместо 400 Bad Request.
