### Слайд 1: Приветствие

Но современный веб устроен так, что сервер и браузер общаются не только с помощью готовых HTML-страниц. Очень часто сервер занимается исключительно обработкой данных и отправляет их в чистом текстовом виде, а визуальный интерфейс строится на стороне клиента. Тема нашего сегодняшнего урока: "API, JSON, REST. Создание HTTP API на Django". Мы разберем, как сделать Django "мозгом" нашего приложения, к которому сможет подключиться и сайт на React, и мобильное приложение на Android, и даже Telegram-бот.»

### Слайд 2: Что такое API?
> **Преподаватель:** «Давайте начнем с базового понятия. Что такое API? Это аббревиатура от Application Programming Interface — интерфейс программирования приложений. Вы каждый день пользуетесь пользовательским интерфейсом (UI) — кнопками, полями ввода, ссылками. Это интерфейс "человек-компьютер". API — это интерфейс "компьютер-компьютер". Это строгий контракт, который говорит одной программе, как вызвать функции другой программы.
> Представьте себе ресторан. Вы пришли пообедать. Вы не идете на кухню сами готовить еду. Вы садитесь за столик и открываете меню. Меню — это API. В нем описано, что вы можете заказать. Вы делаете заказ официанту. Официант — это HTTP-запрос. Он уносит заказ на кухню. Кухня — это сервер, она обрабатывает запрос, готовит блюдо и официант приносит его вам обратно. В этой аналогии блюдо — это нужные данные.»

### Слайд 3: Зачем веб-сайтам нужно API?
> **Преподаватель:** «Зачем усложнять и разделять сайт на API и интерфейс?
> Во-первых, это позволяет разделить разработку Frontend (внешний вид) и Backend (серверная логика). Backend-разработчик пишет один надежный API на Django, а Frontend-разработчики создают интерфейс на современных фреймворках типа React или Vue.
> Во-вторых, одно Backend-приложение может обслуживать много клиентов. Вашему серверу безразлично, кто прислал запрос: браузер, приложение на iPhone, умные часы или скрипт парсера. Они все стучатся на одни и те же URL-адреса и получают одинаково структурированные данные.
> В-третьих, это основа интеграции. Хотите подключить оплату через СБП? Вы будете отправлять запросы к API банка. Хотите вывести карту Яндекс? Используете API Яндекс.Карт.»

### Слайд 4: REST — архитектурный стиль
> **Преподаватель:** «Чтобы разработчики в разных уголках мира понимали друг друга, при проектировании API принято следовать общему стилю. Самым популярным стилем в вебе является REST — Representational State Transfer (передача репрезентативного состояния).
> API, построенное по этим правилам, называют RESTful API.
> Ключевая концепция REST — это **Ресурс**. Ресурсом может быть всё, что угодно: студент лагеря, книга в библиотеке, задача в планировщике. Каждый ресурс имеет свой уникальный адрес — URI (Uniform Resource Identifier).
> Посмотрите на примеры на слайде. Для получения списка всех студентов мы обращаемся к `/api/students/`. А чтобы получить информацию о студенте с ID 5, мы обратимся к `/api/students/5/`. Путь говорит сам за себя, здесь нет глаголов вроде `get_student` или `delete_user`. Только существительные во множественном числе!»

### Слайд 5: 6 ограничений REST
> **Преподаватель:** «Создатель REST Рой Филдинг выделил 6 обязательных ограничений для систем, которые хотят называться RESTful:
> 1. *Client-Server (Клиент-Сервер).* Клиент и сервер независимы. Мы можем полностью переписать клиентскую часть, не меняя код сервера.
> 2. *Stateless (Отсутствие состояния).* Сервер не хранит данные о предыдущих действиях клиента. Запрос `/api/students/5/` выполнится одинаково хорошо, совершил ли клиент до этого 100 запросов или зашел первый раз. Вся информация для авторизации (например, токен) должна передаваться в каждом запросе.
> 3. *Cacheable (Кэширование).* Ответы сервера должны явно указывать, можно ли их кэшировать, чтобы клиент зря не переспрашивал данные, которые редко меняются.
> 4. *Uniform Interface (Единообразие интерфейса).* Все запросы к ресурсам должны выглядеть одинаково, использовать стандартные HTTP-методы и возвращать данные в едином формате, чаще всего JSON.
> 5. *Layered System (Слоистая система).* Клиент не знает, с каким конкретно сервером он общается. На пути запроса могут стоять прокси-серверы, балансировщики нагрузки или системы безопасности.
> 6. *Code on Demand (Код по запросу).* Необязательное требование. Сервер может передавать клиенту исполняемый код, например, JS-файлы для динамического выполнения.»

### Слайд 6: Формат JSON
> **Преподаватель:** «Мы упомянули единообразие формата. Самым популярным текстовым форматом обмена данными сегодня является JSON — JavaScript Object Notation.
> Несмотря на название, JSON не привязан к JavaScript. Это просто текст специального формата, который отлично понимают и Python, и C++, и Java. Он компактен, легко читается человеком и быстро обрабатывается компьютерами.
> Посмотрите на экран. Данные записываются в виде пар "ключ": значение, очень похожих на словари в Python. Ключи всегда пишутся в двойных кавычках.»

### Слайд 7: Типы данных: JSON и Python
> **Преподаватель:** «Давайте сопоставим типы данных JSON с типами данных в Python. Это очень важно для правильной сериализации.
> * Строки в JSON обрамляются строго двойными кавычками `"name": "Иван"`. В Python допускаются и одинарные.
> * Числа записываются без кавычек и транслируются в `int` или `float`.
> * Объект JSON `{}` превращается в словарь Python `dict`.
> * Массив `[]` преобразуется в список Python `list`.
> * Логические значения пишутся с маленькой буквы: `true` и `false`, а в Python — с большой: `True`, `False`.
> * Пустое значение в JSON обозначается словом `null`, в Python это наш привычный `None`.»

### Слайд 8: Сериализация и десериализация в Python
> **Преподаватель:** «В Python есть отличный встроенный модуль `json`, который умеет превращать объекты в строку JSON и наоборот.
> Процесс превращения словаря Python в строку JSON для отправки по сети называется **Сериализацией** (за это отвечает функция `json.dumps`). Обратите внимание на аргумент `ensure_ascii=False` — если его не указать, русские буквы превратятся в нечитаемые коды вида `\u0410`.
> Процесс превращения строки JSON, пришедшей из сети, в словарь Python называется **Десериализацией** или парсингом (за это отвечает функция `json.loads`).»

### Слайд 9: Django и JSON: класс JsonResponse
> **Преподаватель:** «Обычно представления Django возвращают `HttpResponse` с HTML-текстом. Чтобы вернуть JSON-ответ, мы импортируем специальный класс `JsonResponse`.
> Он принимает словарь, самостоятельно превращает его в JSON-строку и добавляет заголовок `Content-Type: application/json`. Браузер, получив такой ответ, сразу понимает, что это структурированные данные, а не просто текст или разметка.»

### Слайд 10: Возврат списков и параметр safe
> **Преподаватель:** «Если вы попытаетесь передать в `JsonResponse` не словарь, а список, например `["Миша", "Лена"]`, Django выдаст ошибку `TypeError`.
> Почему? Исторически существовала уязвимость в старых браузерах, позволявшая похитить данные, если массив JSON находился на самом верхнем уровне ответа. Для защиты Django по умолчанию требует передавать только словари.
> Но если вам действительно нужно вернуть массив данных (что в API происходит постоянно), вы должны явно передать именованный аргумент `safe=False`. Это отключит проверку на словарь и позволит сериализовать список.»

### Слайд 11: Сериализация моделей Django вручную
> **Преподаватель:** «Теперь о самом главном. Мы пишем `JsonResponse(Participant.objects.all())` и... получаем ошибку. Почему? 
> Модуль `json` не умеет превращать сложные объекты классов Django (такие как `QuerySet` или экземпляры моделей) в строку JSON. Нам нужно вручную перевести их в простые типы данных: списки и словари.
> Посмотрите на пример на слайде. Мы берем QuerySet из базы данных, запускаем цикл, вручную собираем словарь для каждого участника и складываем эти словари в список `data`. После этого мы отдаем список в `JsonResponse(data, safe=False)`. Это и есть ручная сериализация. На практике для больших проектов используют Django Rest Framework (DRF), но чтобы понять, как всё устроено изнутри, мы обязаны научиться делать это вручную.»

### Слайд 12: CRUD и HTTP-методы в REST API
> **Преподаватель:** «Как понять, какое действие хочет совершить клиент? В REST API действие кодируется HTTP-методом запроса.
> Аббревиатура CRUD расшифровывается как:
> * **C**reate (Создать) — HTTP-метод `POST`. Отправляется на адрес коллекции, например `/api/students/`. Ожидаемый статус успешного ответа: `201 Created`.
> * **R**ead (Прочитать) — HTTP-метод `GET`. Запрос на коллекцию вернет список объектов, а запрос на `/api/students/5/` вернет детали конкретного студента. Статус: `200 OK`.
> * **U**pdate (Обновить) — методы `PUT` (полная замена объекта) или `PATCH` (частичное изменение отдельных полей). Отправляются на конкретный объект. Статус: `200 OK`.
> * **D**elete (Удалить) — метод `DELETE` на конкретный объект. При успешном удалении данных нет, поэтому возвращается пустой ответ со статусом `204 No Content`.»

### Слайд 13: GET: Чтение и фильтрация параметров
> **Преподаватель:** «Иногда нам нужно получить не весь список объектов, а отфильтровать его по какому-то признаку. В REST API для этого используются query-параметры.
> Например, клиент делает запрос: `/api/participants/?age=15`.
> В Django-представлении мы можем перехватить этот параметр с помощью словаря `request.GET.get('age')`. Если параметр передан, мы применяем фильтр ORM: `queryset.filter(age=age_filter)`. Это позволяет делать гибкие поисковые эндпоинты.»

### Слайд 14: Прием JSON в POST-запросе
> **Преподаватель:** «Когда клиент создает объект, он шлет JSON-данные в теле POST-запроса. 
> Для извлечения этих данных мы обращаемся к свойству `request.body`. Оно возвращает сырую строку байтов. Мы десериализуем её с помощью `json.loads(request.body)`.
> Внимание на декоратор `@csrf_exempt`. Мы помним, что Django защищает POST-запросы от межсайтовой подделки с помощью CSRF-токенов. Но для API, к которому могут обращаться сторонние скрипты или мобильные приложения, эта защита не подходит, у них нет сессий браузера. Поэтому мы отключаем CSRF-проверку для наших API-представлений с помощью декоратора `@csrf_exempt`.»

### Слайд 15: Валидация данных в REST API
> **Преподаватель:** «Золотое правило разработчика: "Никогда не верь клиенту". Пользователь может прислать пустую строку вместо имени, отрицательное число вместо возраста или вообще не передать обязательное поле.
> Перед тем как сохранить объект в базу данных, мы проверяем значения. Если обнаружены ошибки, мы собираем их в словарь `errors`, возвращаем его клиенту в формате JSON и обязательно устанавливаем статус-код `400 Bad Request`. Это сообщает клиентскому приложению, что запрос был некорректным и его нужно исправить.»

### Слайд 16: PUT и PATCH: Обновление данных
> **Преподаватель:** «Обновление данных также требует парсинга JSON из тела запроса.
> Метод PUT требует передачи всех полей объекта. Но чаще используется PATCH. При частичном обновлении (PATCH) мы проверяем наличие ключа в пришедшем словаре: `if 'name' in data:`. Если ключ есть, мы обновляем соответствующее поле модели. Если ключа нет, поле сохраняет старое значение. После этого мы вызываем метод `.save()` и возвращаем обновленный объект.»

### Слайд 17: DELETE: Удаление ресурса
> **Преподаватель:** «Удаление — самая простая операция. Мы находим объект в БД по первичному ключу (`pk`), который передается через URL. Если объект не найден, возвращаем JSON с ошибкой и кодом `404 Not Found`. Если найден, вызываем метод `.delete()`.
> По правилам хорошего тона REST, успешное удаление должно возвращать статус `204 No Content` без какого-либо текста в ответе. Мы делаем это через вызов базового класса `HttpResponse(status=204)`.»

### Слайд 18: Объединение CRUD в одной View
> **Преподаватель:** «Как спроектировать URL-маршруты для API? Принято разделять их на две группы.
> Первое представление работает со всей коллекцией (например, `/api/participants/`). Оно обрабатывает GET (список) и POST (создание).
> Второе представление работает с конкретным элементом по его `id` (например, `/api/participants/5/`). Оно обрабатывает GET (детали), PUT/PATCH (обновление) и DELETE (удаление).
> Внутри одной View-функции мы просто пишем разветвление `if request.method == 'GET': ... elif request.method == 'POST': ...` и так далее.»

### Слайд 19: Частые ошибки при создании API
> **Преподаватель:** «Давайте зафиксируем основные грабли, на которые наступают новички:
> 1. Забыли декоратор `@csrf_exempt` на POST/PUT/DELETE запросы. Вы получите ошибку `403 Forbidden`.
> 2. Ошибки парсинга JSON (`json.JSONDecodeError`). Если прислать пустой запрос или сломанный JSON, `json.loads` выбросит исключение. Код упадет со статусом 500. Всегда оборачивайте парсинг в `try-except` и возвращайте ошибку 400.
> 3. Забыли `safe=False` при возвращении списка из `JsonResponse`.
> 4. Неправильные коды ответов. Возврат кода `200` при ошибках валидации путает клиентские приложения.»

#### 2. Обработка запросов `camp_api/views.py`
```python
# camp_api/views.py
import json
from django.http import JsonResponse, HttpResponse
from django.views.decorators.csrf import csrf_exempt
from .models import Participant

@csrf_exempt
def participant_collection_api(request):
    """
    Эндпоинт для работы со всей коллекцией участников.
    GET  - Получить список всех участников (с фильтрацией по отряду)
    POST - Создать нового участника
    """
    if request.method == 'GET':
        # Извлекаем query-параметр ?group=
        group_filter = request.GET.get('group')
        queryset = Participant.objects.all()
        
        if group_filter:
            queryset = queryset.filter(group_name__iexact=group_filter)
            
        # Ручная сериализация списка участников
        data = []
        for p in queryset:
            data.append({
                "id": p.id,
                "name": p.name,
                "age": p.age,
                "group_name": p.group_name
            })
        return JsonResponse(data, safe=False)

    elif request.method == 'POST':
        try:
            # Десериализуем входящий JSON-запрос в словарь Python
            data = json.loads(request.body)
        except json.JSONDecodeError:
            return JsonResponse({"error": "Невалидный формат JSON"}, status=400)
            
        name = data.get('name')
        age = data.get('age')
        group_name = data.get('group_name')
        
        # Валидация полей
        errors = {}
        if not name or not isinstance(name, str) or len(name.strip()) == 0:
            errors['name'] = "Поле 'name' обязательно для заполнения и должно быть строкой."
        if age is None or not isinstance(age, int) or age < 7 or age > 18:
            errors['age'] = "Поле 'age' обязательно и должно быть числом в диапазоне от 7 до 18."
        if not group_name or not isinstance(group_name, str) or len(group_name.strip()) == 0:
            errors['group_name'] = "Поле 'group_name' обязательно и должно быть строкой."
            
        if errors:
            return JsonResponse({"errors": errors}, status=400)
            
        # Сохранение объекта в базу данных
        participant = Participant.objects.create(
            name=name.strip(),
            age=age,
            group_name=group_name.strip()
        )
        
        # Возвращаем созданный объект и статус 201 Created
        return JsonResponse({
            "id": participant.id,
            "name": participant.name,
            "age": participant.age,
            "group_name": participant.group_name
        }, status=201)

    # Если метод не GET или POST
    return JsonResponse({"error": "Метод не поддерживается"}, status=405)


@csrf_exempt
def participant_item_api(request, pk):
    """
    Эндпоинт для работы с конкретным участником.
    GET    - Получить детальную информацию
    PATCH  - Частично обновить данные участника
    DELETE - Удалить участника
    """
    # Пытаемся найти объект в БД
    participant = Participant.objects.filter(pk=pk).first()
    if not participant:
        return JsonResponse({"error": f"Участник с id {pk} не найден"}, status=404)

    if request.method == 'GET':
        return JsonResponse({
            "id": participant.id,
            "name": participant.name,
            "age": participant.age,
            "group_name": participant.group_name
        })

    elif request.method == 'PATCH':
        try:
            data = json.loads(request.body)
        except json.JSONDecodeError:
            return JsonResponse({"error": "Невалидный формат JSON"}, status=400)
            
        # Частичное обновление полей
        if 'name' in data:
            name = data['name']
            if not isinstance(name, str) or len(name.strip()) == 0:
                return JsonResponse({"error": "Имя должно быть непустой строкой"}, status=400)
            participant.name = name.strip()
            
        if 'age' in data:
            age = data['age']
            if not isinstance(age, int) or age < 7 or age > 18:
                return JsonResponse({"error": "Возраст должен быть числом от 7 до 18"}, status=400)
            participant.age = age
            
        if 'group_name' in data:
            group_name = data['group_name']
            if not isinstance(group_name, str) or len(group_name.strip()) == 0:
                return JsonResponse({"error": "Отряд должен быть непустой строкой"}, status=400)
            participant.group_name = group_name.strip()
            
        participant.save()
        
        return JsonResponse({
            "id": participant.id,
            "name": participant.name,
            "age": participant.age,
            "group_name": participant.group_name
        })

    elif request.method == 'DELETE':
        participant.delete()
        # Возвращаем пустой ответ с кодом 204
        return HttpResponse(status=204)

    return JsonResponse({"error": "Метод не поддерживается"}, status=405)
```
**Разбор кода:**
*   `@csrf_exempt`: отключает проверку CSRF-токена, разрешая внешние POST/PATCH/DELETE запросы.
*   `json.loads(request.body)`: считывает входящий JSON-пакет. Мы обязательно оборачиваем его в `try-except`, чтобы перехватить `JSONDecodeError` и вернуть статус `400 Bad Request` вместо внутренней ошибки сервера `500`.
*   Фильтрация: Метод GET проверяет наличие `group=...` в URL через `request.GET.get('group')`. Если параметр есть, QuerySet фильтруется в БД.
*   `HttpResponse(status=204)`: возвращает пустой ответ при DELETE-запросе, что соответствует спецификации REST.
*   Код `405`: возвращается, если клиент делает запрос неподдерживаемым методом (например, PUT на коллекцию).

### Упражнение 2. Приветственный эндпоинт с валидацией GET-параметров (Базовый уровень)
**Условие:** Создайте API `/api/greet/`, которое принимает два query-параметра: `name` (имя) и `age` (возраст). Эндпоинт должен возвращать приветствие. Если параметры не переданы или пустые, или возраст не является числом, возвращайте словарь с описанием ошибок и HTTP-статус `400 Bad Request`.

**Входные данные:** GET `/api/greet/?name=Михаил&age=15`
**Ожидаемый ответ (200 OK):**
```json
{
  "greeting": "Привет, Михаил! Тебе 15 лет."
}
```
**Входные данные с ошибкой:** GET `/api/greet/?name=&age=-3`
**Ожидаемый ответ (400 Bad Request):**
```json
{
  "errors": {
    "name": "Имя не должно быть пустым.",
    "age": "Возраст должен быть положительным числом."
  }
}
```
**Подсказки:**
*   Используйте `request.GET.get('name')` и `request.GET.get('age')`.
*   Проверьте возраст: попробуйте преобразовать его в `int` через `try-except`.

**Решение:**
```python
# views.py
from django.http import JsonResponse

def greet_api(request):
    name = request.GET.get('name', '').strip()
    age_str = request.GET.get('age', '').strip()
    
    errors = {}
    
    if not name:
        errors['name'] = "Имя не должно быть пустым."
        
    age = None
    if not age_str:
        errors['age'] = "Возраст обязателен для заполнения."
    else:
        try:
            age = int(age_str)
            if age <= 0:
                errors['age'] = "Возраст должен быть положительным числом."
        except ValueError:
            errors['age'] = "Возраст должен быть целым числом."
            
    if errors:
        return JsonResponse({"errors": errors}, status=400)
        
    return JsonResponse({
        "greeting": f"Привет, {name}! Тебе {age} лет."
    })

# urls.py
# path('greet/', views.greet_api, name='greet_api'),
```
**Объяснение решения:**
Мы считываем GET-параметры. Так как они приходят в виде строк, мы преобразуем `age` в `int` и проверяем на ошибки в блоке `try-except`. Если словарь `errors` заполнен, возвращаем его со статусом 400. Если валидация пройдена, возвращаем приветственный текст.

### Упражнение 3. Список курсов с фильтрацией (Базовый уровень)
**Условие:** Создайте эндпоинт `/api/courses/`, который отдает список учебных курсов лагеря из статического списка словарей (без БД). Поддержите фильтрацию по направлению (`direction`) через GET-параметры. Если направление указано, вернуть только те курсы, которые к нему относятся. Если не найдено курсов для направления — возвращать пустой список (200 OK).

**Входные данные:** GET `/api/courses/?direction=web`
**Ожидаемый ответ:**
```json
[
  {
    "title": "Django Web Development",
    "direction": "web",
    "hours": 36
  }
]
```
**Подсказки:**
*   Создайте список словарей `COURSES` внутри файла представлений.
*   Отфильтруйте список с помощью спискового включения (List Comprehension).
*   Не забудьте указать `safe=False` в `JsonResponse`.

**Решение:**
```python
# views.py
from django.http import JsonResponse

COURSES = [
    {"title": "Django Web Development", "direction": "web", "hours": 36},
    {"title": "Advanced Python & Algorithms", "direction": "python", "hours": 40},
    {"title": "Frontend (HTML/CSS/JS)", "direction": "web", "hours": 30},
    {"title": "Robotics & Microcontrollers", "direction": "hardware", "hours": 45},
]

def courses_list_api(request):
    direction = request.GET.get('direction', '').strip().lower()
    
    filtered_courses = COURSES
    if direction:
        filtered_courses = [c for c in COURSES if c['direction'] == direction]
        
    return JsonResponse(filtered_courses, safe=False)

# urls.py
# path('courses/', views.courses_list_api, name='courses_list_api'),
```
**Объяснение решения:**
Мы храним данные в переменной `COURSES`. При запросе проверяем наличие параметра `direction`. С помощью генератора списка фильтруем данные по совпадению направления в нижнем регистре. Результат оборачиваем в `JsonResponse(..., safe=False)`, так как корнем ответа является список.

### Упражнение 4. Детали Участника и ручная сериализация (Средний уровень)

{

### Упражнение 5. Создание Участника с парсингом JSON (Средний уровень)
**Условие:** Напишите POST-эндпоинт `/api/participants/create/`, создающий нового участника. Данные передаются в формате JSON.
Валидация:
*   `name` — непустая строка.
*   `age` — целое число от 7 до 18.
*   `group_name` — непустая строка.
При успешном создании вернуть объект с кодом `201 Created`. При невалидном JSON вернуть `400 Bad Request`.

**Входные данные:** POST-запрос с телом `{"name": "Иван Смирнов", "age": 12, "group_name": "Второй отряд"}`.
**Ожидаемый ответ (201 Created):**
```json
{
  "id": 15,
  "name": "Иван Смирнов",
  "age": 12,
  "group_name": "Второй отряд"
}
```
**Решение:**
```python
# views.py
import json
from django.http import JsonResponse
from django.views.decorators.csrf import csrf_exempt
from .models import Participant

@csrf_exempt
def participant_create_api(request):
    if request.method != 'POST':
        return JsonResponse({"error": "Метод должен быть POST"}, status=405)
        
    try:
        data = json.loads(request.body)
    except (json.JSONDecodeError, TypeError):
        return JsonResponse({"error": "Невалидный или пустой JSON"}, status=400)
        
    name = data.get('name')
    age = data.get('age')
    group_name = data.get('group_name')
    
    errors = {}
    if not name or not isinstance(name, str) or len(name.strip()) == 0:
        errors['name'] = "Имя должно быть непустой строкой."
    if age is None or not isinstance(age, int) or age < 7 or age > 18:
        errors['age'] = "Возраст должен быть числом от 7 до 18."
    if not group_name or not isinstance(group_name, str) or len(group_name.strip()) == 0:
        errors['group_name'] = "Название отряда должно быть непустой строкой."
        
    if errors:
        return JsonResponse({"errors": errors}, status=400)
        
    participant = Participant.objects.create(
        name=name.strip(),
        age=age,
        group_name=group_name.strip()
    )
    
    return JsonResponse({
        "id": participant.id,
        "name": participant.name,
        "age": participant.age,
        "group_name": participant.group_name
    }, status=201)

# urls.py
# path('participants/create/', views.participant_create_api, name='participant_create_api'),
```
**Объяснение решения:**
Мы оборачиваем разбор `request.body` в `try-except` для перехвата невалидных JSON-файлов. Мы проводим жесткую валидацию типов и диапазонов данных. В случае успеха объект сохраняется через ORM `.create()` и возвращается клиенту с кодом HTTP 201.

### Упражнение 6. API списка задач: Полный REST CRUD (Сложный уровень)
**Условие:** Реализуйте полноценный API для управления задачами лагерного проекта.
Создайте модель `Task` с полями: `title` (CharField), `description` (TextField, необязательно), `is_completed` (BooleanField, по умолчанию False).
Напишите два эндпоинта:
1. `/api/tasks/` — поддерживает:
   *   `GET` — возвращает список всех задач.
   *   `POST` — создает новую задачу (требуется только `title`, `description` опционально).
2. `/api/tasks/<int:pk>/` — поддерживает:
   *   `GET` — детальная информация.
   *   `PATCH` — частичное обновление (`title`, `description` или `is_completed`).
   *   `DELETE` — удаление задачи (возвращает статус 204).

**Решение:**
```python
# models.py
from django.db import models

class Task(models.Model):
    title = models.CharField(max_length=200)
    description = models.TextField(blank=True, default='')
    is_completed = models.BooleanField(default=False)

    def __str__(self):
        return self.title

# views.py
import json
from django.http import JsonResponse, HttpResponse
from django.views.decorators.csrf import csrf_exempt
from .models import Task

@csrf_exempt
def task_collection_api(request):
    if request.method == 'GET':
        tasks = Task.objects.all()
        data = []
        for t in tasks:
            data.append({
                "id": t.id,
                "title": t.title,
                "description": t.description,
                "is_completed": t.is_completed
            })
        return JsonResponse(data, safe=False)
        
    elif request.method == 'POST':
        try:
            data = json.loads(request.body)
        except json.JSONDecodeError:
            return JsonResponse({"error": "Невалидный JSON"}, status=400)
            
        title = data.get('title')
        description = data.get('description', '')
        
        if not title or not isinstance(title, str) or len(title.strip()) == 0:
            return JsonResponse({"error": "Поле 'title' обязательно и должно быть строкой."}, status=400)
            
        task = Task.objects.create(
            title=title.strip(),
            description=description
        )
        return JsonResponse({
            "id": task.id,
            "title": task.title,
            "description": task.description,
            "is_completed": task.is_completed
        }, status=201)
        
    return JsonResponse({"error": "Метод не поддерживается"}, status=405)

@csrf_exempt
def task_item_api(request, pk):
    task = Task.objects.filter(pk=pk).first()
    if not task:
        return JsonResponse({"error": "Задача не найдена"}, status=404)
        
    if request.method == 'GET':
        return JsonResponse({
            "id": task.id,
            "title": task.title,
            "description": task.description,
            "is_completed": task.is_completed
        })
        
    elif request.method == 'PATCH':
        try:
            data = json.loads(request.body)
        except json.JSONDecodeError:
            return JsonResponse({"error": "Невалидный JSON"}, status=400)
            
        if 'title' in data:
            title = data['title']
            if not isinstance(title, str) or len(title.strip()) == 0:
                return JsonResponse({"error": "Заголовок должен быть непустой строкой."}, status=400)
            task.title = title.strip()
            
        if 'description' in data:
            task.description = str(data['description'])
            
        if 'is_completed' in data:
            is_completed = data['is_completed']
            if not isinstance(is_completed, bool):
                return JsonResponse({"error": "Поле 'is_completed' должно быть логического типа."}, status=400)
            task.is_completed = is_completed
            
        task.save()
        return JsonResponse({
            "id": task.id,
            "title": task.title,
            "description": task.description,
            "is_completed": task.is_completed
        })
        
    elif request.method == 'DELETE':
        task.delete()
        return HttpResponse(status=204)
        
    return JsonResponse({"error": "Метод не поддерживается"}, status=405)

# urls.py
# path('tasks/', views.task_collection_api, name='task_collection'),
# path('tasks/<int:pk>/', views.task_item_api, name='task_item'),
```
**Объяснение решения:**
Мы реализовали полноценный RESTful-маршрут с разделением на коллекции и отдельные элементы. 
*   `task_collection_api` обрабатывает запросы на получение всего списка (`GET`) и создание (`POST`).
*   `task_item_api` обрабатывает запросы на конкретную задачу по `pk`: чтение детальной информации (`GET`), частичное обновление (`PATCH`) с проверкой типов обновляемых данных, и удаление (`DELETE`).
*   На каждый неверный HTTP-метод отдается код `405 Method Not Allowed`, что гарантирует чистоту архитектуры API.

## 9. Часто задаваемые вопросы (FAQs)

### 1. Почему браузер отображает ошибку 403 Forbidden, когда я тестирую POST-запрос?
По умолчанию Django требует проверки CSRF-токена для всех небезопасных запросов (POST, PUT, PATCH, DELETE) для предотвращения атак межсайтовой подделки запросов. Но API предназначено для программного взаимодействия, у клиента может не быть сессии и куки. Чтобы отключить эту проверку, навесьте на view-функцию декоратор `@csrf_exempt` из модуля `django.views.decorators.csrf`.

### 2. Зачем нужен параметр `safe=False` в `JsonResponse`?
По спецификации `JsonResponse` ожидает, что коренным объектом JSON будет объект `{}` (в Python — словарь). Это защищает от старой уязвимости кражи данных JavaScript. Если вы передаете список `[]`, Django выбросит ошибку. Аргумент `safe=False` отключает это поведение и позволяет передавать списки.

### 3. Как проверить наше API, если обычный браузер умеет делать только GET-запросы?
Для полноценного тестирования API (POST, PUT, DELETE запросы с телом JSON) используют специальные инструменты:
*   Программы вроде Postman или Insomnia.
*   Расширения для VS Code (например, **Thunder Client** или **REST Client**).
*   Консольную утилиту `curl` в терминале.

### 4. В чем разница между `json.dumps` и `json.dump`? И между `loads` и `load`?
*   Методы с буквой **s** на конце (`dumps`, `loads`) работают со **строками** (strings). `dumps` превращает словарь в строку, `loads` парсит строку в словарь.
*   Методы без **s** (`dump`, `load`) работают с **файлами**. `dump` записывает данные в открытый файл на диске, `load` считывает JSON из файла.

### 5. Что произойдет, если клиент отправит невалидный JSON, например, забудет закрыть фигурную скобку?
Функция `json.loads(request.body)` выбросит исключение `json.JSONDecodeError`. Если его не обработать через `try-except`, Django вернет клиенту ошибку `500 Internal Server Error` с куском лога. Это неправильно. Мы должны перехватить исключение и вернуть статус `400 Bad Request` с сообщением о неверном формате.

### 6. Почему при удалении ресурса (DELETE) принято возвращать код 204?
Статус-код `204 No Content` означает, что сервер успешно выполнил запрос, но тело ответа пустое. Так как ресурс удален, возвращать о нем данные нет смысла. Это стандарт соглашения REST API.

### 7. Какая разница между методами PUT и PATCH?
*   `PUT` заменяет ресурс **полностью**. Клиент обязан прислать все поля объекта. Если какое-то поле опущено, оно должно быть удалено или заменено на значение по умолчанию.
*   `PATCH` обновляет ресурс **частично**. Клиент присылает только те поля, которые изменились. Остальные поля в базе данных остаются нетронутыми.

### 8. Как получить GET-параметры из строки запроса?
Все параметры, идущие после знака `?` в URL (например `/api/users/?status=active&grade=9`), Django складывает в словарь-подобный объект `request.GET`. Достать их во View можно с помощью безопасного метода `request.GET.get('имя_параметра')`.

### 9. Можно ли передать файлы через REST API?
Да, файлы передаются либо закодированными в строку Base64 внутри стандартного JSON, либо в бинарном формате с использованием заголовка `Content-Type: multipart/form-data`. Но обычный JSON для передачи больших файлов неэффективен.

### 10. Как обрабатывать авторизацию в REST API, если мы не используем сессии?
В REST API используется авторизация на основе токенов (Token/JWT-авторизация). Клиент отправляет логин/пароль на специальный эндпоинт, сервер проверяет их и возвращает длинную строку-токен. Клиент сохраняет этот токен и прикладывает его ко всем последующим запросам в HTTP-заголовке `Authorization: Bearer <token>`.

### 11. Что такое Content-Type и почему он важен?
`Content-Type` — это HTTP-заголовок, указывающий тип медиаданных в запросе или ответе. Для REST API критически важно возвращать `Content-Type: application/json`, чтобы клиентские библиотеки автоматически преобразовывали текст ответа в объекты данных. `JsonResponse` ставит этот заголовок автоматически.

### 12. Можно ли использовать сериализатор самого Django вместо ручного составления словарей?
Да, в Django есть встроенный модуль `django.core.serializers`. Однако его стандартный вывод ориентирован на внутренние нужды Django (содержит поля `model`, `pk`, а сами данные лежат в объекте `fields`), что не соответствует классическим REST-стандартам и неудобно для фронтенд-разработчиков. Поэтому на практике сериализуют данные либо вручную (как на этом уроке), либо используют Django Rest Framework.

## 10. Методические примечания

### Сложные концепции для объяснения подросткам:
1.  **Отсутствие состояния (Statelessness):** Детям, привыкшим к классическим сайтам с сессиями (где сервер "помнит" залогиненного пользователя), сложно понять, почему в REST сервер забывает клиента сразу после ответа.
    *   *Аналогия:* Представьте турникет в метро. Он не помнит вас лично и не знает, сколько раз вы сегодня ездили. Всё, что ему нужно — приложить билет (токен) в момент прохода. Есть билет — проходите. Нет билета — ошибка 401. Каждый проход автономен.
2.  **Сырой поток байтов (`request.body`):** Ученики часто путают обычный `request.POST` (который Django парсит автоматически для HTML-форм) с `request.body` (сырым JSON-текстом).
    *   *Аналогия:* `request.POST` — это когда вам прислали посылку, в которой вещи уже разложены по подписанным кармашкам (Django сделал работу за вас). `request.body` — это запечатанный ящик с вещами. Чтобы им воспользоваться, вам нужно его вскрыть (декодировать байты) и самостоятельно разобрать содержимое (`json.loads`).

### Стратегии дифференциации обучения:

*   **Для отстающих / слабо подготовленных учеников:**
    *   Сфокусируйте их внимание на GET-запросах (задачи 1, 2, 3). Научите их просто отдавать готовые структуры данных из Django в браузер.
    *   Вместо сложного ветвления методов в одной View разрешите им создавать отдельные функции под каждое действие: `task_list`, `task_create`, `task_delete` с отдельными маршрутами. Это снизит уровень абстракции.
*   **Для сильных / одаренных учеников:**
    *   Предложите им добавить обработку ошибок с помощью блока `try-except` на уровне обращения к ORM (например, ловить `ValidationError` базы данных, если длина строки превышает лимит).
    *   Попросите их реализовать базовую токен-авторизацию: проверять наличие специального секретного ключа в заголовках запроса (`request.headers.get('X-Camp-Token') == 'secret'`), и если токена нет — возвращать `401 Unauthorized`. Это приблизит практику к реальной промышленной разработке.
